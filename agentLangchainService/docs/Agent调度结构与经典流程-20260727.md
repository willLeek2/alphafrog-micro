# Agent 调度结构与经典流程

本文只解释当前实现，不把未来设计写成已经具备的能力。建议先看“六层结构”和“阅读顺序”，再按经典流程跟一次日志。

## 一、整体结构

当前调度不是一个线程池，而是六层互相独立、通过持久状态衔接的控制面。

| 层 | 负责什么 | 不负责什么 |
|---|---|---|
| Run 准入与槽位 | 限制同时执行的 Agent Run，维护 core/max/FIFO queue | 不管理 Sandbox 容器 |
| 工作流路由 | 首次执行前选择 LINEAR 或 DAG | 不负责 ToolJob 恢复 |
| Todo 与工具循环 | 执行 Todo、调用 LLM/工具、生成节点事件 | 不长期占着等待外部任务 |
| ToolJob 挂起与恢复 | 保存 anchor/checkpoint，轮询外部 job，终态收口后恢复原 Todo | 目前不支持 DAG frontier 恢复 |
| 数据分析容量账本 | 在创建 Sandbox 任务前做 STANDARD/HEAVY 准入和 unit 记账 | 不等于 Sandbox 自动伸缩 |
| Python Sandbox | 排队、准备容器、执行代码、保存结果 | 不决定 Java 侧能否进入 |

最容易混淆的是最后两层：Java 的 `DataAnalysisCapacityService` 先做准入。它返回 `SERVER_BUSY` 时，请求根本没有到 Sandbox，所以 Sandbox 即使有自动伸缩也不会被触发。

本次调整把 Java 侧默认 `maxUnits/maxActive/maxHeavyActive` 配成 `20/20/6`，与
`docker-compose.yml` 的 Sandbox 默认 `maxConcurrency=20` 对齐；三个值都有独立环境变量，
生产可按宿主机内存下调。HEAVY 仍消耗 3 units，因此最多同时准入 6 个 HEAVY。

## 二、推荐阅读顺序

### 1. 先看 Run 怎么进入线程池

1. `AgentLangchainRunService`：创建 Run，申请调度 reservation。
2. `LangchainRunConcurrencyScheduler`：core、max、FIFO queue、释放和提升。
3. `LangchainRunAsyncConfig`：物理线程池；物理 queue 固定为 0，唯一业务队列在 scheduler。
4. `LangchainRunExecutorLimits` 与 `LangchainRunExecutorLimitsResolver`：硬上限、当前值和自适应覆盖。
5. `LangchainAdaptiveConcurrencyController`：根据 LLM p90 延迟逐级收缩/恢复 core。

### 2. 再看一个 Run 的主线

1. `LangchainLinearRunPipelineImpl`：planning、路由、执行、终态总控。
2. `LangchainWorkflowRouting`：LINEAR/DAG 裁决。
3. `LangchainLinearWorkflowExecutor` / `LangchainDagWorkflowExecutor`：计划执行。
4. `LangchainTodoNodeExecutor`：单个 Todo 内的 LLM 与工具循环。
5. `ToolRouterToolExecutor` → shared `ToolRouter`：工具调用和事件边界。

### 3. 最后看长工具如何离开前台 worker

1. `PythonSandboxTools`：资源估算、容量 reservation、canonical create、同步快路径。
2. `PythonSandboxDispatchStoreImpl`：把 anchor 与 `WAITING_TOOL_JOB` 一次 CAS 写入 PostgreSQL。
3. `ToolJobCheckpointService`：冻结 plan、已完成 Todo 前缀和当前 Todo。
4. `ToolJobReconciler`：按 due queue 轮询 Sandbox；Redis 丢失时由 PostgreSQL 补扫恢复。
5. `ToolJobFinalizer`：按固定六步释放容量、落账、发事件、生成恢复租约。
6. `ToolJobResumeService` 与 `ToolJobResumeLauncherImpl`：READY→LAUNCHING 抢占和 worker 重入。
7. `LangchainLinearRunPipelineImpl.executeResumedRun`：从原 plan/checkpoint 恢复，不重新 planning。
8. `ToolJobStartupRecovery`：进程重启后重建 PREPARING/PENDING/READY 等状态。

### 4. 配套看容量和 Gateway

1. `DataAnalysisCapacityProperties`：STANDARD/HEAVY 分类和 Java 逻辑上限。
2. `DataAnalysisCapacityServiceImpl`：PREPARING 前准入、reservation 账本、终态 release proof。
3. `pythonSandbox.proto`：Java 与 Gateway 的任务、幂等和结果协议。
4. `PythonSandboxGatewayServiceImpl`：Dubbo proto 与 Python HTTP 的完整桥接。

## 三、经典普通流程

一个不调用长工具的 LINEAR Run，期望顺序如下：

```text
create Run
  → scheduler.reserve
  → RUNNING 或进入 FIFO queue
  → pipeline planning
  → persist plan
  → PLAN_READY
  → LINEAR executor
  → Todo 1 / Todo 2 / ...
  → final answer
  → COMPLETED / PARTIAL / FAILED
  → worker finally 释放 Run 槽位
  → scheduler 提升队首
```

Run 的业务队列只有一层。`ThreadPoolTaskExecutor` 不再保存隐藏 backlog，因此 scheduler 的 running/queued 指标就是实际准入状态。

## 四、经典长 executePython 流程

当前只有实现了 durable adapter 的 `executePython` 可以安全执行“快路径超时后转后台”。默认快路径阈值是 `agent.tool-job.fast-path-ms=1500`。

```text
Todo 调用 executePython
  → 冻结 dataset snapshot、operationId、fingerprint
  → DataAnalysisCapacityService.reserve
       PREPARING，先占 unit 和 pre-create 名额
  → PostgreSQL 保存 PREPARING anchor
  → Gateway canonical createTask
  → 保存 taskId，reservation 变 TASK_ATTACHED
  → 在 1.5 秒快路径内轮询
       ├─ 已终态：同步验证、释放、返回结果
       └─ 仍运行：reservation 变 PENDING_TRANSFERRED
                 anchor + Run 状态 CAS 为 WAITING_TOOL_JOB
                 保存 LINEAR checkpoint
                 当前 Run worker 返回并释放槽位
  → ToolJobReconciler 独立轮询 Sandbox
  → 发现终态并取得结果
  → ToolJobFinalizer 固定六步
       1. ENVELOPE：冻结终态、结果摘要、usage
       2. RELEASE：凭 reservation + terminal proof 释放容量
       3. USAGE：幂等落资源用量
       4. EVENT：幂等发唯一终态工具事件
       5. CAS_STATUS：WAITING_TOOL_JOB → RECEIVED
       6. RESUME_READY：生成 token/lease，进入 READY
  → ResumeService 抢占 READY → LAUNCHING
  → Run scheduler 重新取得 worker
  → executeResumedRun 恢复原 plan、完成前缀和原 Todo
  → 注入工具结果，继续后续 Todo
  → 恢复租约 CONSUMED，清理 anchor/due cache
```

上述每一步都先写 PostgreSQL 真相源，再依赖 Redis 做加速。进程在任意两步之间崩溃，启动恢复或补扫都从首个未完成步骤继续。

## 五、为什么不能把任意同步工具包一层 Future

Java 方法运行超过阈值后，不能只把线程扔到后台：

- JVM 重启后 Java 栈和 Future 都会丢失；
- 不知道外部副作用是否已经发生，重试可能重复写入；
- 没有稳定 operationId/fingerprint，无法 find-or-create；
- 没有结果句柄、checkpoint、release proof 和恢复租约；
- 取消只能停本地等待，不能可靠取消远端工作。

因此统一规则是：

```text
SYNC_ONLY
FAST_PATH_THEN_BACKGROUND
ALWAYS_BACKGROUND
```

每个工具必须显式选择策略。只有提供稳定幂等身份、外部 jobId、状态/结果查询、超时、取消和终态释放协议后，才能选择后两种。当前 `executePython` 是 `FAST_PATH_THEN_BACKGROUND`；其他普通工具仍为 `SYNC_ONLY`。

## 六、当前 DAG 边界

现有 checkpoint 只表达一个 LINEAR Todo 的完成前缀和一个 ToolJob anchor，不能表达：

- DAG 并行 frontier；
- 多个同时运行的外部 ToolJob；
- 每个节点独立的挂起、恢复和 fencing token。

所以启用代码解释器时，pipeline 会在调用 planner 前直接请求 LINEAR。两阶段 planner
会把这个约束同时写入 strategy 与 Todos 提示，并把第一阶段误回的 DAG strategy 正规化为
LINEAR 后再进入第二阶段；最终 Todos 若仍携带 `dependsOn`、`groupKey` 或
`parallelizable`，则 fail-closed 重试，不能通过机械删边猜测执行顺序。首次执行、
`PLAN_READY`、PostgreSQL `planJson` 和恢复路径使用同一份有效 LINEAR 计划。它不是把已经
挂起的 DAG 降级；未来完成 DAG frontier checkpoint 和一对多 ToolJob 表后，才能移除这个隔离。

## 七、取消、重启与幂等

- 取消有活跃 ToolJob 的 Run 时，先写 `runDisposition=CANCELED`、禁止 autoResume，但保留 `WAITING_TOOL_JOB` 的数据库 CAS 前置条件。
- Sandbox 终态到达后仍按 ENVELOPE→RELEASE→USAGE→EVENT 收口，最后才把数据库 Run 写成 CANCELED。
- Redis pending/due 丢失不等于任务丢失；启动恢复和周期补扫以 PostgreSQL anchor 重建。
- `operationId` 和 `requestFingerprint` 用于 create RPC 响应不确定时查回已有任务，不能盲目创建第二个。
- operation lookup 的 `found=false` 只有在 `error` 为空时才是“权威不存在”；transport/5xx/
  解析异常必须保留 PREPARING，不能释放容量或重放 create。
- canonical create/lookup 必须返回与请求完全相同且非空的 fingerprint；正常 create 响应
  若缺失或漂移，必须先按 operationId 回读并同时确认相同 taskId。仍不能证明时保留
  PREPARING 隔离，不能进入普通 PENDING/reconciler 消费路径。
- READY/LAUNCHING 使用 token 与单调 leaseVersion 防止旧 worker 重放结果。

## 八、排障时先看什么

1. Run 状态、`tool_job_anchor_json`、checkpointVersion。
2. estimate 与 reservation 的 `resourceClass/capacityUnits` 是否一致。
3. reservation state 是否卡在 PREPARING、TASK_ATTACHED 或 PENDING_TRANSFERRED。
4. Sandbox task 是否已经 SUCCEEDED/FAILED，但 finalizerStep 仍停在 ENVELOPE/RELEASE。
5. 是否出现 `TOOL_CALL_SUSPENDED`、`TOOL_CALL_FINISHED`、`WORKFLOW_RESUMED`。
6. resumeState/token/leaseVersion 是否停在 READY 或 LAUNCHING。
7. Java `usedUnits/maxUnits/maxActive` 与 Sandbox worker/queue 指标要分开看。

本次 `20260727-084612` 的典型异常正是：Sandbox 任务已经成功，但 estimate 为 `HEAVY/3`、reservation 为 `STANDARD/1`，终态 envelope 校验失败，RELEASE 无法推进，两个 Run 因此一直停在 `WAITING_TOOL_JOB`，后续请求又被泄漏的 Java units 提前拒绝为 `SERVER_BUSY`。
