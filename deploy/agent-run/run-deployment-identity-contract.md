# Agent Run 的部署身份与泳道标签合同

## 1. 要解决的问题

一个 Agent Run 可能在线程池里执行，也可能等待长工具数分钟，或者在服务重启后继续。入口请求结束以后，线程局部变量已经不能说明这个 Run 属于哪个部署、哪一代代码和哪个测试泳道。本合同固定三项事实：

- Run 由实际受理请求的 Agent 实例写入可信部署身份，入口服务不猜测下游身份。
- 泳道标签作为 Run 的不可变属性落库；每次重新取得执行权时，从 Run 行重建线程上下文。
- 旧实例切走流量后自然处理已经受理的工作，统一期限耗尽才停止；切流本身不能批量终止 Run。

部署控制器只管理实例、注册和停止期限，不查询 Run、Todo、事务或业务恢复状态。

## 2. 持久化字段

`alphafrog_agent_run` 保存以下三项不可变字段：

| 字段 | 含义 | 约束 |
|------|------|------|
| `deployment_id` | Run 属于哪个部署环境 | `stable`，或 3 至 64 位小写字母、数字、连字符；首尾为字母或数字；创建后不可修改 |
| `deployment_generation_id` | 受理 Run 的不可变代码与镜像代际 | `gen-` 加 64 位小写十六进制字符；历史迁移值可以是 `legacy-stable`；创建后不可修改 |
| `lane_tag` | 测试请求的泳道标签 | 可空；非空时为 1 至 96 位小写字母、数字、点、下划线、连字符，首尾为字母或数字；创建后不可修改 |

普通流量的 `lane_tag` 为 `null`。`main-beta` 是部署范围名称，不是泳道标签，也不得写入该列。升级迁移为历史 Run 填充既有稳定部署身份，`lane_tag` 保持 `null`。

数据库触发器拒绝修改这三项。普通执行的状态推进、计划、检查点和终态，暂停与取消，启动恢复，以及长工具恢复和收尾，都用原状态与部署身份共同作为同一条 SQL 的条件，防止旧线程覆盖暂停、取消、终态或其他代际的数据。只读服务的到期标记和扩展字段维护不属于业务执行推进，继续使用各自既有条件。

升级已有数据库时，先停止旧 Agent 写入，再执行
`python3 migrate/migrate.py migrate --auto --to current`。迁移工具会扫描当前分支的升级目录，依次执行
`migrate/migrations/upgrades/v1.5/001_agent_run_deployment_identity.sql` 和
`migrate/migrations/upgrades/v1.5/002_agent_run_lane_tag.sql`，并写入迁移记录。自动检测数据库版本失败时，先人工核对当前版本，再用
`python3 migrate/migrate.py migrate --from v1.1 --to current` 显式指定起点。第一份迁移为历史记录补
`stable + legacy-stable`，并把无法安全恢复的历史非终态 Run 写成明确终态；第二份迁移增加
可空的 `lane_tag` 并扩展不可变触发器。迁移完成后必须核对字段、约束和迁移记录，再启动新 Agent。

### 2.1 部署代际算法

部署代际由部署单版本 `manifestVersion`、40 位小写十六进制 Git 提交标识 `gitCommit`，以及
部署单中全部服务的不可变镜像引用共同计算。镜像引用格式为
`<repository>@sha256:<64 位小写十六进制字符>`。

服务先按 `serviceName` 的 ASCII 字符升序排列，再用 UTF-8 拼接下面的字节串。`\n` 是一个
换行字节，`\0` 是一个零字节。

```text
alphafrog-deployment-generation-v1\n
manifest-version:<manifestVersion>\n
git-commit:<gitCommit>\n
service:<serviceName>\0<immutableImageReference>\n
```

对完整字节串计算 SHA-256，在 64 位小写十六进制结果前加 `gen-`。公共 Java 实现是
`common/src/main/java/world/willfrog/alphafrogmicro/common/deployment/DeploymentGenerationId.java`；
跨语言固定向量是 `deploy/agent-run/deployment-generation-test-vector.json`。部署控制器和其他实现
必须通过同一向量，不能改用 JSON 序列化文本或操作系统换行计算。

## 3. 受理与后续请求

### 3.1 创建 Run

入口服务只负责认证测试请求并设置服务器端泳道标签。创建请求里的旧 `deployment_id` 与 `deployment_generation_id` 协议字段仅为兼容旧调用方保留，服务端不读取、不信任，也不回显其值。

实际接收创建请求的 Agent 实例执行以下步骤：

1. 从 `DeploymentIdentityProvider` 读取本机 `AF_DEPLOYMENT_ID` 与 `AF_DEPLOYMENT_GENERATION_ID`。
2. 从 `LaneContext` 读取当前内部泳道标签；没有标签时得到 `null`。
3. 在创建 Run 的同一次插入中写入部署标识、部署代际和泳道标签。
4. 使用插入后返回的同一个 Run 对象进入调度器。

部署身份缺失或格式不合法时，Agent 提供者拒绝启动，不得用默认值创建无法追溯的 Run。

### 3.2 继续对话、暂停、取消和手动恢复

后续请求先按用户与 Run 标识读取数据，再把 Run 已保存的部署身份与当前 Agent 实例身份比较：

- 两项逐字一致才允许继续。
- 不一致时返回“原测试部署已经停用或请求到达错误实例”，不得把 Run 静默迁移到新代际。
- 请求携带的旧部署身份字段不参与授权判断。

泳道标签不由后续请求覆盖。一个 Run 从创建到终态始终使用创建时保存的标签。

## 4. 标签连续性

`LaneContext` 使用 [Alibaba TransmittableThreadLocal](https://github.com/alibaba/transmittable-thread-local)（在线程池提交任务时复制并在结束后恢复上下文的库）。它解决线程池任务提交和执行可能发生在不同线程的问题，但不能代替数据库；跨分钟挂起和跨进程恢复仍以 Run 行为准。

所有业务执行入口使用同一个 `RunLaneContextScope`：

1. 取得完整 `AgentRun`。
2. 用 `run.laneTag` 覆盖执行线程当前标签。
3. 执行业务任务。
4. 在 `finally` 中恢复线程原值，防止线程复用导致下一条 Run 串标。

统一入口必须覆盖：

- 新 Run 的异步执行；
- 长工具完成后的进程内续跑；
- 服务启动后的崩溃恢复。

长工具锚点不重复保存泳道标签，因为标签属于整个 Run。恢复器先读 Run，再通过统一入口重建上下文。随后发出的内部 Dubbo（服务间远程调用框架）调用由公共集群过滤器在标签路由选实例之前把 `dubbo.tag` 写入本次调用，并在调用完成后恢复原上下文。

泳道已经删除时，Run 仍保留原标签。只要 Beta 注册中仍有该服务的无标签主 Beta 实例，Dubbo 的非强制标签路由会先落主 Beta；整个 Beta 注册对该服务都没有可用实例时，同区优先集群才会落生产。若主 Beta 已不存在、但其它带标签泳道实例仍在，官方两层路由无法越过这些实例改选生产，因此部署侧必须先恢复主 Beta。删除泳道本身不把 Run 判为失败，完整回落约束由 Beta 部署合同固定。

## 5. 代际切换与自然排空

更新服务时的顺序固定为：

1. 候选实例健康后进入可选注册。
2. 旧实例从 Nacos 注销；从这一步开始不再接收新流量。
3. 控制器向旧容器发送 `SIGTERM`，Docker 使用部署单中所有服务统一的处理期限等待退出。
4. 旧 Agent 在 Spring 关闭事件开始时停止接收新的 Run；已经受理的 Run、长工具续接和结果持久化继续按正常逻辑运行。关闭监听器在公共处理期限中预留收尾余量，默认 60 秒公共期限与 5 秒收尾余量对应 55 秒自然处理窗口。提前收到线程中断只会记录中断并继续等待，不得提前批量终止 Run。
5. 自然处理窗口结束时，旧 Agent 只把本部署代际仍然非终态的 Run 写为 `FAILED`，错误码为 `deployment_generation_shutdown_deadline_exceeded`，随后用剩余余量完成持久化和进程退出。这个写入发生在切流和自然处理之后，不能在候选健康、旧注册摘除或关闭线程提前中断时触发。公共处理期限耗尽后，容器运行时才执行强制停止。
6. 若旧进程来不及写入就被强制停止，或关闭期间数据库写入失败，其它 Agent 实例上的有界清扫器负责补漏。清扫器在查询和更新两层都排除稳定环境，也不处理本机当前代际；它会轮转扫描仍有未结束 Run 的 Beta 代际，不能让长期存活且排序靠前的代际挡住后续记录。存活核对会遍历 Beta 分组中的全部服务名与全部集群，只有连续一个完整处理期限都找不到目标身份的任何实例，并在写库前再查一次，才能用独立 SQL 分批补写遗留 Run 的失败终态。每轮默认最多更新 32 条，可配置值的硬上限是 256。任一注册查询失败都会让当前候选和本轮剩余候选停止写入，并重新计算全部连续缺席时间；失败发生前已经提交的其它候选写入不会回滚。数据库查询或更新失败只停止本轮数据库动作，不会被记录成注册现场不确定。

不存在退役专用 RPC、退役凭证或退役专用启动模式。候选健康、注册摘除和切流不会改写 Run；只有自然处理窗口结束时的本代关闭收尾，以及确认整代已消亡后的有界补漏，才能写失败终态。部署控制器不查询 Run，也不调用业务终态接口。

## 6. Nacos 与部署配置

Agent 容器由部署控制器注入以下运行配置：

- 当前部署标识与代际；
- 统一关闭期限；
- Nacos 地址、规范化命名空间和 Beta 分组，供清扫器枚举这个分组中的全部服务和集群并核对代际消亡；
- 清扫开关与连续缺席期限，缺席期限必须等于部署单的统一处理期限。

每个 Beta 实例注册时必须保存 `alphafrog.deployment-id` 和 `alphafrog.deployment-generation-id`。主 Beta 实例没有静态泳道标签；泳道实例同时保存 Dubbo 官方静态标签 `dubbo.tag` 与便于注册现场核对的镜像字段 `tag`，两者等于部署的泳道名称。

## 7. 安全与隐私

部署标识、代际和泳道标签可以进入内部日志与调用追踪字段，但不得替代用户授权。外部 HTTP 请求携带的同名头在入口被剥离，只有服务器端名单与口令校验成功后才能建立泳道标签。

本合同不再使用 Agent 退役凭证。历史配置中的 `AF_DEPLOYMENT_RETIREMENT_TOKEN` 与 `AF_DEPLOYMENT_RETIREMENT_ONLY` 必须删除，日志、状态与接口也不得继续声称存在这套能力。

## 8. 验收

至少验证以下行为：

- 调用方伪造部署身份时，创建 Run 仍保存实际受理 Agent 的身份。
- 普通 Run 的 `lane_tag` 为 `null`，泳道 Run 保存服务器端标签，三项身份字段不能更新。
- 新异步执行、长工具续跑和崩溃恢复都在业务代码运行前重建标签，结束后线程上下文恢复。
- Run 标签对应的泳道已删除时，调用按官方路由回落，不因环境删除直接终止 Run。
- 切流只摘旧注册；旧 Run 在处理期限内可以正常完成，不存在退役 RPC 或切流批量终态。
- 正常关闭事件先停止新 Run 准入并等待存量工作；只有公共期限扣除收尾余量后的自然处理窗口结束，才把本代遗留 Run 写为失败，提前中断不能缩短该窗口。
- 清扫器忽略稳定环境和当前代际，轮转覆盖全部候选；它跨 Beta 分组内全部服务和集群核对注册，不确定时不写库，连续缺席期限到达后仍要二次核对，每轮默认写入 32 条且硬上限为 256 条。
- 仓库中不存在退役 RPC、退役凭证或退役专用进程；关闭与清扫写入都有期限、代际和非终态条件。

单元测试与静态合同不能证明真实 PostgreSQL、Nacos、Dubbo、容器信号和强制停止时序。上线前还需要在获准环境中演练一次正常自然排空、一次自然处理窗口结束后的本代失败收尾，以及一次强停或数据库短暂失败后的跨实例有界补漏。
