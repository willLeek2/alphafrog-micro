# AlphaFrog 潜在 GC 场景

## 先说明经历范围

AlphaFrog 目前没有发生过由我们确认并处理的 GC 事故，也没有一份现成的 GC 日志、JFR 或堆转储能够证明线上已经存在内存问题。下面内容来自代码审视，是一项潜在风险分析练习。面试时必须保留这个说明，不能把它包装成真实故障复盘。

## 选择的业务场景

我会选择“用户打开 Agent 任务列表，系统为每条任务计算是否存在分析产物”这个场景。

列表页最终只需要一个“有或没有产物”的标记。当前业务流程为了得到这个标记，会对本页每条任务进入完整的产物查询：读取任务的全部历史事件，把事件和内部载荷反序列化，关联 Python 调用、并行任务、待办项与数据集，再构造完整产物列表，最后只判断列表是否为空。

这个流程具有三种放大因素：

1. 单页任务数可以从默认数量提高到一百条。
2. 长任务可能积累较多历史事件，完整读取没有事件数量限制。
3. 多名用户并发刷新列表时，多套事件列表、字符串、映射和 JSON 节点会在堆中同时存在。

代码已经限制单条事件和工具预览的大小，因此这里更值得怀疑的是许多中小对象带来的分配压力，以及请求处理期间较大的活跃对象集合。仅凭代码还不能断言存在内存泄漏，也不能断言会产生 G1 巨型对象。

## 为什么这个场景适合校招回答

它的业务语义和技术代价存在明显差距：页面只需要一个布尔标记，系统却完成了全量历史读取、JSON 解析、跨事件关联和产物构造。候选人可以先从业务流程减少无效工作，再讨论 JVM 配置，体现自己理解 GC 问题通常由对象生命周期和数据规模共同形成。

项目中还存在 SSE 连接、事件恢复缓冲和定时任务等内存候选，但这些流程已经具备快照数量、分页数量、单连接缓冲数量和断开清理。它们仍应测试，只是当前代码给出的数量限制更清楚。任务列表的完整历史解析更适合本次练习。

## 第一部分：怎样发现

我会先为任务列表增加业务观测，并按三个维度分组：一页有多少任务、每个任务有多少事件、同时有多少列表请求。需要观察的指标包括请求 P95/P99、事件总数、事件载荷总量、对象分配速率、Young GC 次数、累计停顿、回收后堆占用和进程总内存。

然后构造对照测试：

- 页面任务数分别采用二十和一百。
- 任务分别使用短事件历史与长事件历史。
- 并发从单请求逐步提高到预期峰值。
- 一组保留当前产物标记计算，另一组暂时跳过该计算。

如果只有保留当前计算的测试随着“任务数乘以事件数”增加而出现分配速率、GC 次数和延迟同步上升，才说明这个候选流程与现象相关。

面试口述可以说：

> 我不会看到堆上涨就直接说是 GC 问题。我会先把列表页任务数、每个任务的事件数和并发数记录下来，再把请求高分位延迟与 GC 停顿按时间对齐，并设置跳过产物标记计算的对照组。

## 第二部分：怎样排查

第一步读取 GC 日志，确认 Young、Mixed 或 Full 事件的频率、原因、回收前后占用和停顿。第二步在可复现环境采集短时 JFR，查看字符串、字节数组、集合节点和 JSON 解析对象的分配调用栈是否集中在任务历史读取与产物关联流程。第三步比较请求前后的对象直方图。

判断时分成三类：

- 请求结束后回收低点恢复，但 Young GC 和累计停顿增加：更接近分配速率高。
- 请求结束后需要较长时间才能释放，多个并发请求的对象互相重叠：更接近临时活跃对象集合过大。
- 请求结束并经过多轮回收后，对象仍被长期引用，回收低点持续升高：此时才进一步获取堆转储，沿 GC Roots 查看是否存在缓存、会话、定时任务或其他长期持有者。

堆转储和全量对象统计可能影响运行实例。真实环境需要先确认实例余量、磁盘空间和操作权限，优先在复现环境或单个可摘除实例上执行。

面试口述可以说：

> JFR 如果显示大量分配来自完整事件解码和 JSON 解析，同时请求结束后堆低点能够恢复，我会把它判断为高分配和临时对象问题。只有请求结束、多轮回收以后对象仍被长期引用，我才会使用“内存泄漏”这个判断。

## 第三部分：怎样解决

第一步直接修改业务查询。列表页先收集本页任务编号，一次批量查询哪些任务存在用户可见的成功产物，只返回任务编号集合，再填充布尔标记。它不需要读取每条事件的完整载荷。

第二步把三个动作分开：列表页只查询是否存在；用户进入产物页时再查询产物元数据；真正查看或下载时才准备文件。这样能够避免普通列表刷新重复执行完整产物构造。

第三步为仍需从事件恢复产物的详情页减少读取量，只选择与 Python 调用和数据集有关的事件类型，并采用分页或流式处理。解析器只保留尚未匹配完成的少量状态，异常事件数量超过限制时记录告警并停止继续扩大内存。

完成程序修改后，再在同等任务数、事件数和并发数下复测。比较请求 P99、分配速率、Young GC、累计停顿、回收后占用、CPU 和吞吐。如果业务修改后容量仍然不足，才评估堆大小、实例规格和收集器目标。

面试口述可以说：

> 我的首选处理是把“为了一个布尔值读取全部历史”改成批量存在性查询，暂时不调整 GC。列表、元数据和文件准备分三个阶段执行。修改后用同一批长任务和相同并发复测；程序分配已经下降但容量仍不足时，再讨论堆或收集器。

## 一段完整的项目回答

> 这个项目没有真实排查过 GC 事故，所以我把下面内容当作风险练习。AlphaFrog 的任务列表需要展示每条任务是否有分析产物。现有流程会为本页每条任务读取完整事件历史，反序列化事件载荷，关联 Python 调用和数据集，构造完整产物列表，最后只取一个布尔结果。长任务和并发刷新可能制造很多短命字符串、集合与 JSON 对象，也会扩大请求期间的活跃对象集合。
>
> 我会先按页面任务数、每任务事件数和并发数压测，把列表延迟与 GC 日志、JFR 分配事件对齐，并用跳过产物标记的请求作为对照。若请求结束后堆低点恢复，就主要检查高分配和临时对象；若多轮回收后低点仍持续升高，再用直方图与堆转储调查长期引用。
>
> 处理上先把列表改成批量存在性查询，只返回有产物的任务编号；产物元数据和文件准备延后到用户真正打开时执行。随后用同等负载比较 P99、分配速率、停顿和回收后占用。业务流程已经减少无效对象但容量仍不足时，我才会评估堆和收集器。

## 面试官继续追问时

**“你凭什么说这里会发生 Full GC？”**

不能凭代码直接这样判断。代码只能说明存在分配放大候选。是否发生 Full GC，需要 GC 日志、堆占用、并发量与压测结果证明。

**“这算内存泄漏吗？”**

目前没有泄漏证据。多数中间对象应在请求结束后失去引用。只有它们在多轮回收后仍被缓存、会话、任务或其他长期对象持有，才可以称为泄漏。

**“扩大堆是否也能解决？”**

它可能延后回收并提高峰值容量，但不会减少列表页重复执行的全量读取和解析。应先删除这部分无效工作，再根据真实工作集决定容量。
