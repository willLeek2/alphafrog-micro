# Java GC 校招面经与回答模板

## 先看结论

如果面试官直接问“线上 GC 频繁怎样排查”，可以先用下面这段回答，再按后文逐项回答连续追问：

> 我会先记录用户影响、发生时间和当时负载，再用 GC 日志、进程指标与系统日志确认是否真的与 GC 有关。随后区分对象分配过快、存活对象持续增加、堆容量不合适、元空间或原生内存问题。根据分类选择 JFR、对象直方图或堆转储定位对象和引用关系。处理时先修改批量大小、缓存生命周期、无界集合等业务设计，再根据服务目标考虑堆大小和收集器。最后在相同流量与数据规模下比较停顿、吞吐、回收后占用和错误率。

后文先给出 17 组基础问题的主回答与追问回答，再给出 18 道场景题。中文面经只用于确认真实问法；技术答案以 Oracle Java 文档、Java 语言规范和 OpenJDK JEP 为事实依据。

## 基础问题与连续追问

下面每个问题都提供可直接口述的回答。回答后的追问也给出完整说法。事实结论使用 Java SE 25、OpenJDK JEP 与 2024 年以来校招面经交叉核验。

### 1. “你了解 Java GC 吗？”

**可直接回答**：

> Java GC 是 JVM 的自动内存管理机制。类实例和数组通常分配在堆中，JVM 会判断对象是否仍能被运行中的程序访问；无法继续到达的对象进入可回收范围，原来占用的堆空间可以重新使用。自动管理减少了手工释放内存带来的错误，但仍有运行成本：GC 会占用 CPU，部分阶段会暂停应用线程，长期存活对象还会扩大每次回收需要处理的工作量。因此我会同时关注内存占用、吞吐和停顿，不会只关注“有没有回收”。

**追问：“有 GC 就不会内存泄漏了吗？”**

**追问回答**：

> 仍然可能泄漏。GC 判断的是对象是否可达，不理解对象还有没有业务价值。一个已经失去业务用途的对象只要仍被静态集合、缓存、线程局部变量、监听器或其他长期对象引用，GC 就会把它当作存活对象。Java 内存泄漏通常表现为这类无用但仍可达的对象不断积累。

**追问：“GC 能管理文件句柄和网络连接吗？”**

**追问回答**：

> GC 主要管理 Java 对象占用的内存，不能保证文件句柄、Socket 和数据库连接及时释放。这些资源需要明确关闭，适合使用 `try-with-resources`。终结机制的执行时间无法保证，而且已经被 OpenJDK 标记为待移除，不能作为常规资源释放方案。

**核验依据**：[Oracle Java 25 MemoryMXBean](https://docs.oracle.com/en/java/javase/25/docs/api/java.management/java/lang/management/MemoryMXBean.html)、[Java SE 25 JLS 12.6.1](https://docs.oracle.com/javase/specs/jls/se25/html/jls-12.html#jls-12.6.1)、[OpenJDK JEP 421](https://openjdk.org/jeps/421)。

### 2. “JVM 内存区域有哪些，GC 主要处理哪里？”

**可直接回答**：

> 面试里我会分成三组。第一组是 Java 堆，类实例和数组从这里分配，GC 主要回收堆中不可达对象。第二组是非堆内存，包含方法区的实现数据，例如类元数据、运行时常量，以及 JVM 为内部处理和 JIT 编译代码使用的内存。HotSpot 中常见的观察项有元空间和代码缓存。第三组是进程中的其他原生内存，例如线程栈、直接缓冲区和本地库分配。排查 OOM 时需要先确认是哪一组出现问题，因为堆转储无法解释全部原生内存增长。

**追问：“线程栈里的对象会被 GC 吗？”**

**追问回答**：

> Java 语言层面常说对象分配在堆中，栈帧保存局部变量和引用。栈中的引用可以让堆对象继续可达。JIT 可能通过逃逸分析消除某些对象分配，但面试回答不应把“对象一定在栈上分配”当成语言保证。

**追问：“堆很稳定，容器仍被 OOMKilled，可能是什么原因？”**

**追问回答**：

> 容器限制约束进程总内存。元空间、线程栈、直接内存、JIT 代码和本地库都可能继续增长。此时应该查看容器事件、线程数、直接内存与原生内存统计，同时检查 `-Xmx` 是否给这些区域保留了足够余量。

**核验依据**：[Oracle Java 25 MemoryMXBean](https://docs.oracle.com/en/java/javase/25/docs/api/java.management/java/lang/management/MemoryMXBean.html)、[Oracle Java 25 内存泄漏排查](https://docs.oracle.com/en/java/javase/25/troubleshoot/troubleshooting-memory-leaks.html)。

### 3. “JVM 怎样判断对象可以回收？”

**可直接回答**：

> JVM 采用可达性分析。可以把对象关系理解成一张引用图：从仍可能参与后续计算的起点出发，沿引用向外遍历，能够到达的对象属于存活对象；已经无法通过这些路径到达的对象，才具备回收条件。具备回收条件不代表调用结束后马上释放，实际回收时间由收集器和内存压力决定。

这里需要区分“引用计数”和“可达性分析”。简单引用计数会给每个对象记录引用数量，处理循环引用比较困难；可达性分析从一组起点检查整张引用图，两个对象即使互相引用，只要整体无法从这些起点到达，仍然可以回收。

**追问：“两个对象互相引用，能回收吗？”**

**追问回答**：

> 可以。假设 A 引用 B，B 也引用 A，但线程、静态字段和其他存活对象都不再引用 A 或 B，那么这个小环整体无法从存活起点到达，二者都具备回收条件。

**追问：“对象进入不可达状态后一定马上回收吗？”**

**追问回答**：

> 不保证。不可达只说明对象具备回收条件。JVM 何时启动回收、选择哪些区域以及何时重新使用空间，都由收集器和当时内存压力决定。`System.gc()` 也只要求 JVM 尽力回收，不保证回收某个数量的对象或在某个时间完成。

**核验依据**：[Java SE 25 JLS 12.6.1](https://docs.oracle.com/javase/specs/jls/se25/html/jls-12.html#jls-12.6.1)、[Oracle Java 25 `java.lang.ref`](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/ref/package-summary.html)、[Oracle Java 25 `System.gc()`](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/System.html#gc())。

### 4. “GC Roots 通常有哪些？”

**可直接回答**：

> GC Roots 是可达性分析的起点。校招回答可以列出四类常见来源：正在运行的线程栈中使用的引用；类的静态字段引用；JNI 或 JVM 内部保存的原生引用；同步监视器、类加载器等 JVM 仍需维护的对象。回答时我会补一句：不同 JVM 实现展示的 Root 分类名称可能不同，但判断原则相同，程序后续计算或 JVM 运行仍然需要的对象会形成存活起点。

**追问：“为什么静态集合容易造成泄漏？”**

**追问回答**：

> 静态字段通常随类和类加载器长期存活。静态集合中的元素会沿引用路径保持可达。如果集合不断增加，又没有删除、过期或容量限制，已经没有业务用途的元素也无法回收。

**追问：“局部变量离开方法后，对象一定能回收吗？”**

**追问回答**：

> 只能说明当前栈帧不再通过这条局部变量引用它。对象还可能被返回值、其他集合、异步任务或静态字段引用。需要确认所有存活路径都消失，不能只看某一条引用。

**核验依据**：[Java SE 25 JLS 12.6.1](https://docs.oracle.com/javase/specs/jls/se25/html/jls-12.html#jls-12.6.1)、[Oracle Java 25 G1 工作方式](https://docs.oracle.com/en/java/javase/25/gctuning/garbage-first-g1-garbage-collector1.html)。

### 5. “强、软、弱、虚引用有什么区别？”

**可直接回答**：

> 强引用是普通引用，只要对象仍然强可达，GC 就不会回收。软引用在内存压力下可以被清理，适合表达可丢弃数据，但不适合承担必须可预测的缓存容量管理。弱引用不会让对象因为这条引用继续保持强存活，常用于对象关联表等场景。虚引用无法通过引用直接取得对象，通常与引用队列配合，用于获知对象进入回收生命周期后的状态并处理相关清理工作。

**追问：“软引用适合实现业务缓存吗？”**

**追问回答**：

> 一般业务缓存更需要明确的容量、过期时间和淘汰策略。软引用的清理时机由 JVM 和内存压力决定，命中率与容量不容易预测。它可以表达“内存不足时允许丢弃”，却不能替代完整缓存策略。

**追问：“虚引用能保证外部资源及时释放吗？”**

**追问回答**：

> 不能保证及时。引用队列和清理动作仍受 GC 时机影响。必须及时释放的文件、连接与锁应采用明确关闭流程。

**核验依据**：[Oracle Java 25 `java.lang.ref`](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/ref/package-summary.html)、[OpenJDK JEP 421](https://openjdk.org/jeps/421)。

### 6. “为什么 JVM 要分年轻代和老年代？”

**可直接回答**：

> 分代利用了一个常见现象：多数对象存活时间很短。新对象主要进入年轻代，年轻代填满后只处理这一部分；多数对象已经死亡时，回收成本主要取决于少量存活对象。经过多次回收仍然存活的对象会逐步进入老年代。这样可以频繁处理短命对象，同时减少每次都扫描全部存活对象的成本。

> 这个设计也带来新的观察项。对象创建过快会提高 Young GC 频率；年轻代存活对象过多会增加复制和晋升；老年代存活对象持续增长会提高后续回收压力。因此排查时要同时观察分配速率和回收后存活量。

**追问：“所有新对象都在年轻代吗？”**

**追问回答**：

> 不能写成绝对规则。具体收集器、对象大小和 JVM 优化会影响分配位置。校招回答可以说“多数普通新对象进入年轻代”，大对象和特殊分配需要结合收集器日志判断。

**追问：“年龄达到阈值才会晋升吗？”**

**追问回答**：

> 对象年龄是常见条件之一，Survivor 空间不足、动态年龄判断和分配担保等情况也会影响晋升。面试中先说明“多次存活后通常晋升”，面试官继续询问时再展开具体收集器行为。

**核验依据**：[Oracle Java 25 分代回收](https://docs.oracle.com/en/java/javase/25/gctuning/garbage-collector-implementation.html)。

### 7. “标记清除、复制、标记整理分别怎样工作？”

**可直接回答**：

> 标记清除先找出存活对象，再回收其余空间，实现简单，但释放后可能留下分散空洞。复制算法把存活对象移动到新的连续空间，原区域可以整体复用；当存活对象较少时效率较高，但需要目标空间，也会产生对象移动成本。标记整理在标记后把存活对象向一侧移动，形成连续空闲空间，减少碎片，代价是移动较多存活对象和更新引用。

> 这些是回收算法思路。垃圾收集器是 JVM 中把标记、并发、并行、对象移动、区域选择和停顿控制组合起来的具体实现。G1 主要通过对象转移回收选中的 Region，转移本身也会完成压缩。

**追问：“为什么年轻代常采用复制思路？”**

**追问回答**：

> 年轻代通常死亡对象多、存活对象少。复制少量存活对象后即可整体复用原区域，避免逐块维护大量空洞。若存活对象比例升高，复制成本和目标空间压力也会增加。

**追问：“为什么老年代不能永远只做标记清除？”**

**追问回答**：

> 长期只留下分散空洞，会让大对象或连续分配难以找到足够空间。收集器需要通过整理、对象转移或区域管理处理碎片问题，具体方式取决于实现。

**核验依据**：[Oracle Java 25 G1 工作方式](https://docs.oracle.com/en/java/javase/25/gctuning/garbage-first-g1-garbage-collector1.html)、[Oracle Java 25 分代回收](https://docs.oracle.com/en/java/javase/25/gctuning/garbage-collector-implementation.html)。

### 8. “常见垃圾收集器有哪些，怎样选择？”

**可直接回答**：

> Serial 使用单个 GC 线程，适合资源较少或小堆场景。Parallel 使用多个 GC 线程，主要目标是吞吐。G1 把堆划分为多个 Region，结合分代、并行和大部分并发工作，按照停顿目标选择每次处理的工作量，适合多数需要兼顾吞吐与停顿的服务。ZGC 把大量耗时工作与应用并发执行，面向更严格的低延迟目标，也需要足够 CPU 和堆余量。

> 选择时先给出 JDK 版本、堆大小、吞吐目标、允许停顿和 CPU 余量，再用代表性负载比较。没有严格停顿要求时，可以先采用 JVM 的默认选择建立基线。收集器名称本身不能替代压测结果。

**追问：“G1 一定比 Parallel GC 好吗？”**

**追问回答**：

> 两者目标不同。批处理任务若更关注总吞吐并能接受较长停顿，Parallel 可能更合适；交互式服务若关注高分位延迟，G1 的停顿目标更容易表达需求。最终仍要比较吞吐、停顿、CPU 和内存成本。

**追问：“ZGC 停顿低，为什么不全部使用 ZGC？”**

**追问回答**：

> 低停顿只是一个目标维度。JDK 版本、吞吐、CPU 余量、堆大小、运维工具和团队经验都会影响选择。ZGC 仍需要为存活对象和并发回收期间的新分配保留空间，也并非完全没有停顿。

**核验依据**：[Oracle Java 25 Available Collectors](https://docs.oracle.com/en/java/javase/25/gctuning/available-collectors.html)、[Oracle Java 25 ZGC](https://docs.oracle.com/en/java/javase/25/gctuning/z-garbage-collector.html)。

### 9. “CMS 和 G1 有什么差异？”

**可直接回答**：

> CMS 的设计目标是降低老年代回收停顿，它以并发标记和清除为主要思路，不主动完成常规压缩，因此需要处理碎片、浮动垃圾和并发失败。G1 使用 Region 管理堆，通过并发标记掌握各 Region 的存活量，再在多次停顿中优先转移回收收益较高的区域；对象转移同时完成压缩。G1 还可以根据历史数据调整每次停顿的工作量，尝试满足停顿目标。

> 版本信息必须说明：CMS 已在 JDK 14 移除。现代项目讨论 CMS 时通常是在解释旧系统、历史迁移或比较设计思路，新项目不能把它当成当前可选收集器。

**追问：“CMS 为什么会产生浮动垃圾？”**

**追问回答**：

> 并发清除期间应用线程仍在运行，也会继续产生新垃圾。当前回收周期可能无法处理这部分新产生的垃圾，需要留到后续周期，因此需要预留空间。

**追问：“G1 就没有并发失败或碎片问题了吗？”**

**追问回答**：

> G1 仍可能因分配速度过快、对象无法顺利转移或空间不足而发生转移失败，严重时进入 Full GC。Region 和对象转移改善了碎片管理，但不能消除容量、分配和大对象压力。

**核验依据**：[OpenJDK JEP 363](https://openjdk.org/jeps/363)、[Oracle Java 25 G1 工作方式](https://docs.oracle.com/en/java/javase/25/gctuning/garbage-first-g1-garbage-collector1.html)。

### 10. “STW、并行和并发分别是什么意思？”

**可直接回答**：

> STW 表示应用线程在某个 GC 阶段暂停。并行表示多个 GC 线程同时执行回收工作，应用线程通常处于暂停状态；并发表示 GC 线程与应用线程在同一时间段共同运行。一个收集器可以同时包含这三种特征，例如 G1 的全局标记大部分可以并发执行，对象转移仍在 STW 停顿中并行完成。

> 并发能够减少长时间暂停，但会与应用争用 CPU，也需要处理应用继续修改引用关系的问题。看到“并发收集器”时，不能推导出完全没有停顿。

**追问：“为什么对象转移通常需要停顿？”**

**追问回答**：

> 对象移动后，所有相关引用都要指向新位置。暂停应用线程可以避免应用同时读取或修改正在移动的对象，降低一致性处理难度。低延迟收集器会使用更复杂的屏障和并发移动技术，但仍可能保留很短的暂停阶段。

**核验依据**：[Oracle Java 25 G1 工作方式](https://docs.oracle.com/en/java/javase/25/gctuning/garbage-first-g1-garbage-collector1.html)、[Oracle Java 25 ZGC](https://docs.oracle.com/en/java/javase/25/gctuning/z-garbage-collector.html)。

### 11. “Young GC、Mixed GC、Full GC 有什么区别？”

**可直接回答**：

> 术语需要结合收集器。以 G1 为例，Young GC 主要回收年轻代 Region；Mixed GC 在年轻代回收基础上，同时转移一部分经过标记、回收收益较高的老年代 Region；Full GC 是 G1 在内存压力下的后备流程，会停止应用并对整个堆进行压缩，通常代价更高。

> Major GC 在不同资料中可能表示老年代回收，也可能被混用成 Full GC。面试中我会直接说出收集器和日志事件，例如 `G1 Pause Young`、`G1 Mixed`、`G1 Pause Full`，避免把不同术语强行等同。

**追问：“Young GC 会处理老年代对象吗？”**

**追问回答**：

> Young GC 的回收集合主要是年轻代，但为了正确找到年轻代存活对象，仍需处理从老年代指向年轻代的引用信息。它不会因此变成一次老年代空间回收。

**追问：“Mixed GC 为什么不一次回收全部老年代？”**

**追问回答**：

> G1 希望把老年代回收拆到多次停顿中。每次选择部分收益较高的 Region，能够控制单次工作量，提高满足停顿目标的概率。

**核验依据**：[Oracle Java 25 G1 工作方式](https://docs.oracle.com/en/java/javase/25/gctuning/garbage-first-g1-garbage-collector1.html)。

### 12. “什么情况下会发生 Full GC？”

**可直接回答**：

> 我会先限定为 G1。G1 在应用分配速度过快、并发标记和空间回收来不及完成，或者对象转移无法释放足够空间时，可能退化到全堆 STW 压缩。显式 `System.gc()` 也可能在日志中触发完整回收，具体行为受 JVM 配置影响。其他收集器的 Full GC 触发条件和日志名称会有差异，因此需要以实际收集器和 GC 日志为准。

> 排查时我会查看事件原因、回收前后占用、转移失败、大对象 Region、晋升量和分配速率。只背“老年代满了”无法解释为什么空间回收跟不上。

**追问：“Full GC 一定会回收元空间吗？”**

**追问回答**：

> 不能给出跨版本、跨收集器的绝对答案。类卸载需要类加载器及其加载的类不再可达，也受收集器和类卸载配置影响。日志中可以查看元空间前后占用和类卸载事件。Full GC 发生了，不代表所有无用类都会在这次回收中卸载。

**追问：“怎样减少 Full GC？”**

**追问回答**：

> 先根据触发原因处理。分配过快就减少临时对象和批量峰值；存活对象持续增加就检查缓存、集合和引用生命周期；大对象多就降低单次对象大小或改成流式处理；显式 GC 就查找调用来源；容量确实不足再调整堆和实例规格。修改后用同等负载比较 Full GC、累计停顿、回收后占用和吞吐。

**核验依据**：[Oracle Java 25 G1 工作方式](https://docs.oracle.com/en/java/javase/25/gctuning/garbage-first-g1-garbage-collector1.html)、[Oracle Java 25 `System.gc()`](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/System.html#gc())。

### 13. “Young GC 很频繁说明什么？”

**可直接回答**：

> Young GC 频繁首先说明年轻代很快达到回收条件，常见方向是对象分配速率高、年轻代容量与负载不匹配，或者存活对象较多导致转移和晋升压力。频率高不自动等于故障，也不自动等于泄漏。还要查看单次与累计停顿、回收后占用、晋升量、CPU 和用户延迟。

> 如果每次回收都能释放大部分空间，老年代低点稳定，更接近短命对象多；如果晋升量和老年代低点持续提高，再调查长期存活对象。JFR 的分配事件可以把对象类型和调用栈对应到大 JSON 解析、批量集合、字符串拼接或序列化流程。

**追问：“直接把年轻代调大可以吗？”**

**追问回答**：

> 可能降低回收频率，也可能提高单次回收需要处理的对象数量，并占用更多堆空间。需要比较分配速率、存活比例、停顿和吞吐，再决定是否调整。先减少重复对象通常更容易解释和验证。

**核验依据**：[Oracle Java 25 分代回收](https://docs.oracle.com/en/java/javase/25/gctuning/garbage-collector-implementation.html)、[Oracle Java 25 JFR 性能排查](https://docs.oracle.com/en/java/javase/25/troubleshoot/troubleshoot-performance-issues-using-jfr.html)。

### 14. “Full GC 后老年代仍然很高，怎样判断？”

**可直接回答**：

> 我会区分正常工作集、容量不足和内存泄漏。先在相对稳定的负载下观察多次完整回收后的占用低点。如果低点达到某个水平后保持稳定，可能是缓存、索引或任务状态构成了正常工作集；如果低点持续提高，再比较多个时间点的对象直方图，查看哪些类型的数量和保留大小持续增长。必要时分析堆转储中的支配树和到 GC Roots 的引用路径，确认是谁长期持有这些对象。

> 泄漏要求对象已经没有业务用途却仍然可达。容量不足则是对象都具有业务用途，但当前堆无法容纳峰值工作集。两者可能显示相似曲线，必须结合对象用途和引用路径判断。

**追问：“只拿到一份堆转储能判断泄漏吗？”**

**追问回答**：

> 一份转储可以找到当时占用大的对象和引用关系，却很难证明持续增长。需要结合 GC 后低点、业务时间、多次直方图或持续 JFR。结论应该保留这个限制。

**核验依据**：[Oracle Java 25 内存泄漏排查](https://docs.oracle.com/en/java/javase/25/troubleshoot/troubleshooting-memory-leaks.html)、[Oracle Java 25 Diagnostic Tools](https://docs.oracle.com/en/java/javase/25/troubleshoot/diagnostic-tools.html)。

### 15. “元空间会不会被回收？”

**可直接回答**：

> 元空间保存类元数据。类卸载通常以类加载器失去可达性为前提，单个类无法在加载器仍然存活时随意卸载。是否执行类卸载还受 JVM 实现、收集器和配置影响。排查元空间增长时，应查看已加载类数量、类加载器数量、卸载事件和元空间回收后占用，再检查动态代理、脚本、热部署或插件是否反复创建类加载器。

**追问：“提高元空间上限能解决问题吗？”**

**追问回答**：

> 如果应用确实需要加载更多类，提高上限可以提供容量。如果旧类加载器一直被线程、静态字段或监听器引用，提高上限只会延后 OOM。需要用类加载器统计和引用路径区分。

**追问：“Full GC 之后元空间没有下降，说明泄漏吗？”**

**追问回答**：

> 不能直接判断。当前加载的类可能都在正常使用，也可能这次没有执行类卸载。需要观察多轮变化、类加载器数量和持有引用。

**核验依据**：[Oracle Java 25 MemoryMXBean](https://docs.oracle.com/en/java/javase/25/docs/api/java.management/java/lang/management/MemoryMXBean.html)、[Oracle Java 25 内存泄漏排查](https://docs.oracle.com/en/java/javase/25/troubleshoot/troubleshooting-memory-leaks.html)。

### 16. “OOM 和内存泄漏有什么区别？”

**可直接回答**：

> OOM 表示 JVM 或进程无法满足一次内存请求，它是故障结果。原因可能是堆容量不足、对象泄漏、元空间不足、直接或原生内存不足，也可能是要创建过大的数组。内存泄漏描述的是对象已经没有业务用途，但仍被引用并持续占用资源。泄漏可能最终导致 OOM，也可能在很长时间内只表现为回收后低点提高和 GC 频率增加。

> 排查 OOM 的第一步是读取完整错误信息并确认内存区域。Java heap space 重点查看堆；Metaspace 重点查看类和类加载器；容器 `OOMKilled` 需要查看进程总内存。不能看到“OOM”三个字就直接获取堆转储并宣布堆泄漏。

**追问：“堆 OOM 怎样区分容量不足与泄漏？”**

**追问回答**：

> 在稳定负载下观察完整回收后的存活量，比较多个时间点的对象增长，再分析对象是否仍有业务用途和谁在引用。正常工作集超过容量更接近容量不足；无用对象沿长期引用不断积累更接近泄漏。

**核验依据**：[Oracle Java 25 内存泄漏排查](https://docs.oracle.com/en/java/javase/25/troubleshoot/troubleshooting-memory-leaks.html)。

### 17. “排查 GC 和 OOM 时，各种工具怎样选择？”

**可直接回答**：

> GC 日志回答回收类型、原因、回收前后占用和停顿；`jstat` 适合快速观察各内存区、回收次数和累计时间的趋势；`jcmd` 可以查看堆信息、生成对象直方图、控制 JFR 和获取堆转储；JFR/JMC 适合分析一段时间内的分配、停顿、线程和锁；堆转储配合 MAT 用于查看支配对象、保留大小和到 GC Roots 的引用路径；NMT 与系统指标用于调查原生内存。

> 顺序通常是先用已有日志和低影响指标判断方向，再选择高影响诊断。对象直方图和堆转储可能给大堆带来暂停与磁盘压力，不应在所有线上实例同时执行。

**追问：“`jmap` 和 `jcmd` 选哪个？”**

**追问回答**：

> 当前 Oracle 文档优先介绍 `jcmd`、JFR 和 JMC。Java 25 的 `jmap` 文档把它标为实验性且不受支持。面试官点名 `jmap` 时可以说明它能生成直方图和堆转储，同时补充当前环境会优先使用受支持的诊断方式。

**追问：“为什么一份直方图不够？”**

**追问回答**：

> 它只展示某个时刻各类型的实例数和字节数，无法单独证明增长趋势，也没有完整引用关系。多次直方图适合比较增长，堆转储用于查看持有路径，JFR 补充时间维度。

**核验依据**：[Oracle Java 25 Diagnostic Tools](https://docs.oracle.com/en/java/javase/25/troubleshoot/diagnostic-tools.html)、[Oracle Java 25 `jcmd`](https://docs.oracle.com/en/java/javase/25/docs/specs/man/jcmd.html)、[Oracle Java 25 `jstat`](https://docs.oracle.com/en/java/javase/25/docs/specs/man/jstat.html)。

## 通用回答框架：发现、确认、定位、处理、验证

### 为什么采用这个顺序

接口变慢、CPU 升高、进程退出和内存上涨可能同时出现，也可能互不相关。直接增大堆、切换收集器或重启实例，会改变现场并掩盖原来的证据。先确认问题类型，再选择诊断数据，能够让每一步回答一个明确的问题。

### 第一步：发现用户影响与运行变化

先回答“发生了什么”：

- 接口 P95、P99 延迟是否突然升高？吞吐和错误率怎样变化？
- 进程是否退出，容器是否重启，系统是否记录了 `OOMKilled`？
- 堆占用是否呈锯齿状，回收后低点是否逐次升高？
- GC 次数、累计停顿和 CPU 是否与业务高峰同时变化？
- 最近是否上线了批量查询、文件导出、大缓存、定时任务或新的依赖？

面试中可以补一句：“我会先保存发生时间和受影响请求，后面才能把 GC 日志、应用日志和业务流量按时间对齐。”

### 第二步：确认是否为 GC 或内存问题

观察以下证据：

- GC 日志中的回收类型、触发原因、回收前后占用与停顿时间。
- 进程 CPU、堆、非堆、线程数、直接内存与容器总内存。
- `jstat` 提供的一段连续采样，用于查看各区域占用、回收次数和累计时间；它适合观察趋势，不适合单独证明某个对象泄漏。
- 完整异常信息和系统日志，用于区分 Java 堆 OOM、元空间、线程创建失败与容器终止。

确认阶段需要回答两个问题：用户延迟是否与停顿时间重合；内存问题发生在 Java 堆、非堆还是进程总内存。

### 第三步：根据分类选择定位证据

#### 分配压力

现象通常是 Young GC 频率提高，但每次回收后大部分空间都能释放。可以用 JFR 的分配事件、线程分配统计和调用栈，查看哪些请求或批任务创建了大量临时对象。常见来源包括大 JSON 的反复解析与复制、批量结果一次性装入集合、字符串拼接和序列化中间对象。

#### 存活对象持续增加

现象通常是完整回收后的占用低点逐步升高。可以先比较多次对象直方图，再在合适的实例上生成堆转储，用 MAT 查看大对象、支配树和到 GC Roots 的引用路径。这里要寻找“谁一直引用它”，不能只看到某个类占用大就直接修改。

#### 堆容量或收集器目标不合适

若对象都具有业务用途，引用关系正常，但当前峰值工作集超过堆容量，可以评估堆大小、并发量、批量大小和实例规格。若容量充足，但停顿目标无法满足，再根据 JDK 版本、延迟目标、吞吐与 CPU 余量评估收集器和参数。

#### 元空间、直接内存、线程或原生内存

堆图看起来正常，进程总内存仍然增长时，需要检查类加载数量、线程数、直接缓冲区和本地库。容器事件、系统日志、NMT、线程统计和相关应用指标会比 Java 堆转储更有帮助。

### 第四步：先改业务行为，再评估 JVM 配置

常见程序修改包括：

- 把一次性加载的大批数据改成分页、流式或分块处理。
- 给缓存、集合、事件缓冲和去重记录设置数量或时间限制。
- 在连接结束、任务取消和异常路径中解除引用并取消定时任务。
- 避免同一份大型结果在多个层次重复解析、复制和序列化。
- 修正线程局部变量、监听器、回调和类加载器的长期引用。
- 对突发请求设置并发上限，防止瞬时工作集超过单实例容量。

堆大小和收集器调整并非禁用项。证据表明容量确实不足或停顿目标不匹配时，调整配置是合理操作；只是它应当建立在负载与对象数据之上。

### 第五步：在同等条件下复测

至少比较：

- P95、P99 延迟和错误率。
- Young GC、Full GC 的次数、累计停顿和高分位停顿。
- 每次回收后的堆占用低点。
- 对象分配速率和晋升量。
- 业务吞吐、CPU 与进程总内存。

如果处理的是内存泄漏，还应当让压测持续足够长时间，确认回收后低点不再持续升高。若只跑很短的一轮，可能只能证明瞬时峰值下降。

## 两种可直接口述的版本

### 30 秒版本

> 我不会先改 JVM 参数。我会先确认延迟或进程退出是否和 GC、内存变化同时发生，再从日志判断是 Young GC 频繁、Full GC 频繁、堆 OOM，还是元空间、直接内存或容器总内存问题。堆内问题再用 JFR、对象直方图或堆转储定位分配热点和长期引用。处理时优先修改无界集合、批量大小、缓存生命周期和异常清理，最后才根据停顿与容量目标调整堆或收集器，并用相同负载比较修改前后的停顿、回收后占用和吞吐。

### 两分钟版本

> 我会分五步。第一步记录用户影响、发生时间和当时负载，例如 P99 延迟、错误率、CPU、堆占用与容器重启。第二步用 GC 日志、系统日志和连续指标确认是否与 GC 有关，并区分 Java 堆、元空间、直接内存、线程和容器总内存。第三步根据现象选择证据：Young GC 频繁但回收效果好，我会用 JFR 看分配热点；完整回收后占用仍持续升高，我会比较对象直方图，并在合适实例上分析堆转储和 GC Roots 引用路径；堆正常但进程内存高，我会检查线程、直接缓冲区和原生内存。第四步根据对象来源修改批量处理、缓存、集合、监听器或清理流程，容量确实不足时再调整堆与实例规格，停顿目标不合适时再评估收集器。第五步使用相同流量和数据规模复测，比较延迟、停顿、分配速率、回收后占用、吞吐和错误率，并保留回退方案。

## 场景题答案的事实核验

下面 18 道场景题的问法来自 2024 年以来的校招与实习面经，答案没有采用面经作者的技术结论。各类判断分别按以下官方资料核验：

- Young、Mixed、Full、转移失败和回收阶段：[Oracle Java 25 G1 工作方式](https://docs.oracle.com/en/java/javase/25/gctuning/garbage-first-g1-garbage-collector1.html)。
- 分配速率、存活对象、内存泄漏、堆转储和原生内存：[Oracle Java 25 内存泄漏排查](https://docs.oracle.com/en/java/javase/25/troubleshoot/troubleshooting-memory-leaks.html)。
- JFR 的分配、线程、锁、I/O 与 GC 时间线：[Oracle Java 25 JFR 性能排查](https://docs.oracle.com/en/java/javase/25/troubleshoot/troubleshoot-performance-issues-using-jfr.html)。
- `jcmd`、`jstat`、JFR、对象直方图和堆转储的用途：[Oracle Java 25 Diagnostic Tools](https://docs.oracle.com/en/java/javase/25/troubleshoot/diagnostic-tools.html)。
- 收集器选择与适用目标：[Oracle Java 25 Available Collectors](https://docs.oracle.com/en/java/javase/25/gctuning/available-collectors.html)、[Oracle Java 25 ZGC](https://docs.oracle.com/en/java/javase/25/gctuning/z-garbage-collector.html)。

每道题先给主回答，再给面试官继续询问时可以直接说出的追问回答。

## 校招场景题一：接口周期性变慢，怎样证明是 GC

**题目**：某个 Java 接口平时很快，但每隔一段时间 P99 延迟会出现尖峰。监控里能看到 GC，你怎样判断尖峰是不是由 GC 引起？

**回答**：

1. 记录慢请求时间段、请求量、线程池、数据库与下游延迟。
2. 对齐 GC 日志中的停顿开始时间和持续时间，看尖峰是否与应用线程暂停重合。
3. 同时查看 CPU、锁等待和下游超时，排除业务热点或依赖变慢。
4. 如果多次尖峰都与较长停顿重合，再继续分析是哪类回收、为什么触发以及回收前后占用。
5. 修改后用同样的流量模型复测，比较 P99 与停顿分位数。

**压力追问**：“一次时间重合能证明吗？”

**追问回答**：

不能。一次重合只能形成怀疑，需要多次样本、相同时间窗口中的线程与依赖指标，以及修改后的对照结果。

## 校招场景题二：Young GC 很频繁，但每次很短

**题目**：Young GC 每秒发生多次，但单次停顿不长，你会怎样分析？

**回答**：

先看用户延迟和累计停顿，频率高并不自动等于故障。若累计停顿和 CPU 已经影响吞吐，再看对象分配速率、年轻代回收前后占用、对象晋升量与业务流量。JFR 可以帮助查找分配量较大的线程和调用栈。常见方向是大 JSON 解析、批量集合、字符串与序列化中间对象。处理上优先减少重复解析与复制、缩小单批数据、复用适合复用的缓冲结构；证据显示年轻代容量与负载不匹配时，再评估相关配置。

**压力追问**：“把年轻代调大是否就行？”

**追问回答**：

它可能降低回收频率，也可能延长单次回收或挤压其他区域。需要根据分配速率、晋升量、停顿目标和实际复测决定。

## 校招场景题三：Full GC 频繁，回收后占用明显下降

**题目**：Full GC 次数增加，但每次结束后老年代占用都能明显下降，说明什么？

**回答**：

这说明存在较多可回收对象，暂时不能据此判断泄漏。后续需要查看触发原因、对象晋升、是否存在大对象、显式 GC、元空间压力，以及堆容量是否让完整回收过早发生。若业务高峰创建了短期大结果或批任务，应该先降低瞬时工作集。若触发来自配置或收集器行为，再结合版本和服务目标调整。

**压力追问**：“既然能回收，为什么仍然是问题？”

**追问回答**：

完整回收可能产生较长停顿和额外 CPU。对象最终能释放，只能说明引用没有永久保留，不能说明分配方式和容量安排合理。

## 校招场景题四：Full GC 后老年代仍然很高

**题目**：Full GC 后老年代仍然接近上限，你会怎样区分泄漏与容量不足？

**回答**：

先在相对稳定的负载下观察多次完整回收后的占用低点。如果低点持续升高，再比较多个时间点的对象直方图，查看哪些对象数量与保留大小持续增长。随后分析堆转储中的支配树和到 GC Roots 的引用路径，确认长期引用来自缓存、静态集合、线程局部变量、监听器还是正在执行的业务。若对象都在正常服务当前请求或缓存命中目标，引用关系也符合设计，可能是工作集超过容量；若对象已经没有业务用途却仍被引用，更接近泄漏。

**压力追问**：“只拿到一份堆转储怎么办？”

**追问回答**：

可以先找占用最大的对象、支配关系和引用路径，但无法可靠判断增长趋势。应结合发生前后的 GC 日志、对象年龄、业务时间和后续直方图；结论需要保留不确定性。

## 校招场景题五：出现 Java heap space

**题目**：线上出现 `OutOfMemoryError: Java heap space`，你的第一反应是什么？

**回答**：

先记录完整异常、发生时间、实例与业务影响，保留 GC 日志、JFR 和自动生成的堆转储。如果服务必须先恢复，可以限流、摘除异常实例或扩容，但避免所有实例同时执行高开销诊断。随后检查回收后占用趋势、对象直方图和堆转储，区分大批数据一次性进入内存、无界集合、缓存保留、引用未清理与容量不足。修改后用相同数据规模和持续时间复测。

**压力追问**：“生成堆转储没有风险吗？”

**追问回答**：

堆转储会占用磁盘，也可能增加暂停和 CPU 压力。真实环境需要选择合适实例、确认磁盘容量并遵守操作流程。不能为了取证让剩余实例同时失去服务能力。

## 校招场景题六：容器被 OOMKilled，但堆没有到上限

**题目**：容器被系统终止，监控显示 Java 堆尚未达到 `-Xmx`，你怎样解释？

**回答**：

容器限制约束的是进程总内存，其中 Java 堆只占一部分。元空间、直接缓冲区、线程栈、JIT、共享库和其他原生分配都会占用内存。先看容器事件与系统日志，再比较堆、非堆、线程数、直接内存和进程常驻内存。需要时使用 NMT 或对应组件指标继续定位。处理可能涉及减少线程、限制直接缓冲区、修复本地资源释放、调整堆与容器内存配比，单独增大 `-Xmx` 往往无法处理这类问题。

**压力追问**：“为什么增大堆可能更糟？”

**追问回答**：

容器总内存不变时，更大的堆会减少原生内存的余量，进程可能更早触及容器限制。

## 校招场景题七：CPU 升高，同时 GC 时间增加

**题目**：CPU 突然升高，GC 时间也增加，你会先查哪一个？

**回答**：

先确认 CPU 时间由哪些线程消耗，并对齐业务流量和 GC 事件。大量对象分配可能使 GC 线程消耗更多 CPU；业务死循环、锁竞争或序列化热点也可能先推高 CPU，再间接降低 GC 的运行余量。可以结合 JFR、线程栈、火焰图与 GC 日志区分。回答时不要把“CPU 高且发生 GC”直接解释为“GC 导致 CPU 高”。

**压力追问**：“`jstack` 能直接找到最耗 CPU 的方法吗？”

**追问回答**：

线程栈提供某一时刻的线程状态，单次快照不等于 CPU 分布。通常需要先从系统层找到高 CPU 线程并换算线程标识，再结合多次栈、JFR 或火焰图判断持续热点。

## 校招场景题八：批量导出或大 JSON 导致内存波动

**题目**：某个批量导出接口处理大文件时，Young GC 和 Full GC 都增加，怎样处理？

**回答**：

先测量单次任务的数据量、并发数、峰值堆占用和对象分配，确认是否一次性构造了完整工作簿、全部行对象或多份 JSON 副本。用 JFR 查看分配热点，用堆转储确认任务执行期间保留了哪些大对象。程序侧可改成分页读取、流式写出、限制并发和及时释放中间结果。随后使用相同文件大小与并发数复测，比较峰值占用、累计停顿、任务时长和错误率。

**压力追问**：“异步执行能解决内存问题吗？”

**追问回答**：

异步只能改变请求线程是否等待，不会自动减少对象数量。若后台任务仍然一次性加载全部数据，内存风险仍在；还可能因异步并发增加而放大峰值。

## 校招场景题九：元空间持续增长

**题目**：堆比较稳定，但元空间持续增长并最终 OOM，可能是什么原因？

**回答**：

元空间主要保存类元数据。需要查看已加载类数量、类加载器数量和卸载情况，结合堆转储中的类加载器引用、JFR 类加载事件或相关诊断数据。常见方向包括动态生成大量类、重复创建类加载器、热部署或插件加载后仍有线程、静态字段和回调引用旧类加载器。处理时要解除这些长期引用，控制动态生成数量，并验证类能够卸载。

**压力追问**：“直接提高元空间上限可以吗？”

**追问回答**：

它可以为正常类数量增长提供容量，也可能只是延后类加载器泄漏。需要先观察类和类加载器是否持续增长。

## 校招场景题十：怎样选择 G1、Parallel GC 或 ZGC

**题目**：一个 Java 后端服务应该怎样选择垃圾收集器？

**回答**：

先明确 JDK 版本、堆大小、硬件、吞吐与延迟目标，再以真实负载测量。Parallel GC 偏向吞吐；G1 尝试在较高吞吐下满足停顿目标；ZGC 偏向低延迟，并需要为存活对象和并发回收期间的新分配保留足够空间。没有严格停顿要求时，可以先使用 JVM 的默认选择并建立基线。选择后比较高分位停顿、吞吐、CPU 和内存占用，不能只比较平均停顿。

**压力追问**：“ZGC 停顿低，为什么不全部改成 ZGC？”

**追问回答**：

服务目标、JDK 版本、CPU 余量、堆大小和运维经验不同。低停顿不代表在所有负载下都获得最高吞吐或最低资源成本，需要通过压测决定。

## 校招场景题十一：代码中出现 System.gc()

**题目**：发现业务代码或依赖调用了 `System.gc()`，你会怎样处理？

**回答**：

先通过 GC 日志确认是否触发了显式回收、调用频率与停顿影响，再找到调用来源和业务目的。若调用只是希望“及时释放”，应改为正确管理对象和外部资源；若来自第三方库，需要确认版本、配置和替代方案。是否禁用显式 GC 要结合依赖行为和验证结果，不能仅凭看到调用就修改 JVM 参数。

**压力追问**：“对象设为 null 后调用 System.gc() 能保证释放吗？”

**追问回答**：

不能保证。设为 `null` 只是减少一条引用，其他引用仍可能存在；`System.gc()` 也只是向 JVM 提出建议，具体行为受收集器和配置影响。

## 校招场景题十二：没有处理过生产 GC 事故

**题目**：你简历上写了 JVM，但没有真实生产 GC 调优经历，怎样回答？

**推荐说法**：

> 我没有独立处理过生产 GC 事故，所以不会把风险分析说成线上经验。我做过受控实验：限制堆大小，分别制造大量短命对象和长期保留对象，打开 GC 日志和 OOM 自动堆转储，再用 `jstat`、`jcmd`、JFR 与 MAT 对照分配速率、回收后占用、对象数量和引用路径。这个实验让我能够说明证据怎样支持判断。如果进入真实值班场景，我会先遵守取证和变更流程，再进行影响较小的检查。

**压力追问**：“没有生产事故经验，怎样证明这些步骤可行？”

**追问回答**：

我会展示可重复的实验记录，而不把实验说成生产经验。记录应包含 JDK 版本、收集器、堆限制、输入规模、持续时间、GC 日志、JFR 或堆转储，以及修改前后的同条件对照。面试官可以沿这些证据检查我的判断是否成立。

## 校招场景题十三：对象大量进入老年代

**题目**：监控显示对象晋升量突然增加，随后老年代占用和 Mixed GC 频率提高，你怎样分析？

**回答**：

先查看业务流量、对象分配速率、年轻代回收后的存活量和晋升量是否在同一时间变化。晋升增加可能来自对象确实存活更久，也可能来自年轻代空间、晋升担保或突发批量让对象来不及在年轻代释放。JFR 分配调用栈可以找到对象来源，对象年龄和堆转储可以帮助判断它们为什么存活。

如果来源是一次请求内保留的大集合，可以缩小批量、分页处理或减少中间副本；如果来源是缓存和任务状态，需要检查生命周期与数量限制；如果对象都是必要工作集，再评估容量。只看到晋升增加，不能直接判断老年代泄漏。

**压力追问**：“把晋升年龄调大是否可行？”

**追问回答**：

它会改变对象在年轻代停留的时间和空间压力，可能减少部分提前晋升，也可能提高年轻代回收成本。需要先确认对象来源，再用代表性负载比较停顿、晋升量和吞吐。

## 校招场景题十四：缓存上线后回收低点提高

**题目**：新缓存上线后，Full GC 结束时的堆占用低点提高了，但随后保持稳定。这是泄漏吗？

**回答**：

它更像缓存增加了正常存活对象，暂时不满足“持续增长”的泄漏特征。需要核对缓存条目数、估算单条占用、过期和淘汰规则，并观察稳定负载下的低点是否保持在可接受范围。如果缓存达到设计容量后不再增长，命中收益也符合预期，可以把它视为新的正常工作集；如果条目数超出限制或过期对象仍被引用，再调查实现问题。

**压力追问**：“缓存稳定就一定没有风险吗？”

**追问回答**：

仍需评估峰值请求与缓存工作集叠加后的余量，以及缓存重建时的瞬时分配。稳定只说明没有继续增长，不代表容量和停顿目标一定满足。

## 校招场景题十五：定时任务执行后内存不下降

**题目**：每天一次的批任务结束后，堆占用没有恢复到执行前水平，你会怎样处理？

**回答**：

先确认任务是否真的结束，相关线程、异步子任务和回调是否全部完成。然后比较执行前后和一次回收后的对象直方图，查看增加的是业务结果、缓存、日志缓冲、线程局部变量还是批处理框架对象。若有必要，再使用堆转储查看引用路径。

需要特别注意“任务结束”只是业务状态，后台线程、Future、监听器或定时任务仍可能保存上下文。处理时应当在成功、失败、取消和超时路径中都清理引用，取消不再需要的调度任务，并限制批处理结果的保留时间。

**压力追问**：“手动调用 GC 看内存是否下降可不可以？”

**追问回答**：

在受控测试环境中可以把它作为实验手段之一，但它可能改变停顿和时序，不能替代引用分析。生产环境也不能把周期性显式 GC 当作清理策略。

## 校招场景题十六：应用重启几次后元空间才出问题

**题目**：应用支持动态加载策略，前几次更新正常，多次更新后元空间 OOM，你会怀疑什么？

**回答**：

我会先比较每次更新后的已加载类数量和类加载器数量，看旧类加载器能否卸载。若旧加载器被线程上下文、静态字段、监听器、JDBC 驱动注册或线程局部变量引用，它负责加载的类元数据也无法释放。堆转储中的类加载器视图和 GC Roots 路径可以帮助找到持有者。

处理时要给动态加载流程定义完整生命周期：停止旧线程、注销监听器、清空静态注册、关闭资源并解除加载器引用。复测需要连续执行多轮更新，确认类加载器数量能够回落，不能只验证一次更新成功。

**压力追问**：“已经把加载器变量设为 null，为什么类仍然不能卸载？”

**追问回答**：

一个局部变量消失只会移除一条引用。旧线程的上下文加载器、静态注册表、监听器、线程局部变量或本地组件仍可能引用旧加载器及其类。还要考虑收集器是否执行类卸载，因此需要查看实际加载器引用路径和多轮回收后的数量变化。

## 校招场景题十七：直接内存使用增加

**题目**：网络服务的 Java 堆稳定，进程总内存持续升高，直接内存指标也在增长，你怎样回答？

**回答**：

先检查网络框架、直接缓冲区、文件映射和本地库的使用量，以及缓冲区是否被池化或延迟释放。堆转储可能看到包装对象，却无法完整展示所有原生内存，因此需要结合 NMT、框架指标、线程与系统内存数据。还要确认容器限制与 `-Xmx` 的配比，避免 Java 堆占用挤压原生内存余量。

处理方式取决于证据：修复缓冲区引用或引用计数错误、限制池容量、降低并发读写、缩小单次消息、升级有已知修复的依赖。单纯调整堆不能自动释放直接内存。

**压力追问**：“为什么堆转储不能完整说明直接内存增长？”

**追问回答**：

堆转储主要记录 Java 堆中的对象和引用。直接缓冲区的 Java 包装对象可能出现在堆中，但实际原生内存及本地库分配不一定完整呈现，所以还要结合 NMT、组件指标和进程总内存数据。

## 校招场景题十八：GC 日志没有长停顿，接口仍然很慢

**题目**：接口 P99 很高，但 GC 日志中没有对应的长停顿，你还会继续调 GC 吗？

**回答**：

不会立即继续调 GC。时间没有重合，应该回到线程池排队、锁竞争、数据库、远程调用、磁盘和 CPU 热点。JFR 可以在同一时间线中查看线程、锁、Socket、文件 I/O 和 GC 事件，帮助比较候选原因。GC 可能仍然消耗一部分 CPU，但需要证明它对当前延迟有足够影响。

**压力追问**：“没有长停顿，能完全排除 GC 吗？”

**追问回答**：

不能完全排除。频繁短停顿的累计时间、并发回收消耗的 CPU、对象分配带来的运行开销都可能影响吞吐。仍要比较同一时间窗口的累计停顿、CPU 和请求指标；如果没有足够相关性，就应优先调查线程、依赖和 I/O。

## 怎样读一条 GC 日志

校招面试通常不会要求现场解释一份上千行日志，但可能给出一两条统一日志，让你说出观察顺序。可以按以下顺序回答：

1. **事件类型**：先确认收集器和事件名称，例如 G1 Young、Mixed 或 Full。
2. **触发说明**：查看是正常分配、并发周期启动、显式请求、转移失败还是其他原因。
3. **回收效果**：比较回收前后已使用堆与当前堆容量。下降很多说明可回收对象较多；下降很少说明存活对象较多，但仍需趋势和引用证据。
4. **停顿时间**：看单次停顿和一段时间的累计停顿。一个很短的事件发生得极其频繁，也可能影响吞吐。
5. **业务对齐**：把日志时间与请求延迟、流量、批任务、发布和 CPU 对齐。

假设日志显示某次回收把堆从八百兆降到二百兆，耗时两百毫秒，可以得到两条初步信息：当时存在大量可回收对象；这次停顿可能影响高分位延迟。仍然不能仅凭这一行判断为什么产生这些对象，也不能判断系统是否长期有问题。

若日志显示回收前九百兆、回收后八百五十兆，而且这种低点连续上升，才值得进一步调查存活对象。后续证据应来自多次日志、对象直方图、JFR 或堆转储。

## 怎样设计一个校招可完成的 GC 实验

没有生产事故经历时，一次设计清楚的本地实验比背诵几十个参数更有说服力。可以准备两个小场景。

### 实验 A：大量短命对象

让程序重复解析一批 JSON 或创建短期集合，控制输入规模和循环次数。限制测试 JVM 的堆，打开统一 GC 日志，并采集短时 JFR。预期现象是分配速率提高、Young GC 变频繁，但回收后低点大体稳定。

实验记录至少包含：JDK 版本、收集器、堆大小、输入规模、持续时间、Young GC 次数与累计停顿、JFR 中分配较多的对象和调用栈。随后把重复解析改成一次解析，或缩小批量，再进行对照。

### 实验 B：长期保留对象

让一个有界和一个无界容器分别保存对象。有界容器达到上限后淘汰，无界容器持续保留。观察两者在相同负载下的回收后堆低点和对象直方图，再用堆转储查看无界容器到 GC Roots 的引用路径。

这个实验能够说明“不可达对象”和“没有业务用途但仍然可达的对象”的差异。实验结束后要删除或关闭测试程序，避免把制造 OOM 的代码混入业务服务。

### 面试时怎样介绍实验

> 我用相同输入做了两组实验。一组重复制造短命对象，Young GC 增加但回收后低点稳定；另一组把对象持续放入无界集合，回收后低点不断提高。JFR 帮我找到第一组的分配调用栈，堆转储和 GC Roots 路径帮我确认第二组由长期集合持有。随后我分别减少重复解析、给集合增加容量限制，并在相同条件下复测。

这样的表达包含假设、证据、修改与对照，也诚实限定在本地实验范围。

## 连环追问训练

### 第一组：从“GC 很频繁”开始

**面试官**：“监控说 GC 很频繁，怎么办？”

**候选人**：“我先确认收集器、事件类型、频率、停顿和回收前后占用，并对齐用户延迟。Young GC 频繁但回收后低点稳定，更像分配压力；完整回收后低点持续升高，才继续调查存活对象。”

**面试官**：“怎样查分配压力？”

**候选人**：“用 JFR 的分配事件和线程分配统计查看对象类型与调用栈，再结合请求类型、批任务和序列化流程。”

**面试官**：“找到字符串最多，就说明字符串泄漏吗？”

**候选人**：“不能。字符串可能只是短命分配多。要看回收后是否仍然保留、谁持有引用，以及数量是否在稳定负载下持续增长。”

### 第二组：从“OOM”开始

**面试官**：“出现 OOM，先做什么？”

**候选人**：“保存完整错误、实例、时间和业务影响，区分 Java 堆、元空间、直接内存、线程或容器终止，并保留已有 GC 日志和 JFR。”

**面试官**：“服务已经不可用，难道不先重启？”

**候选人**：“恢复服务和保留证据可以并行安排。可以先摘除异常实例、限流或扩容，再在一台可控实例保留数据。若所有实例直接重启，后续可能无法判断原因。”

**面试官**：“堆转储很大怎么办？”

**候选人**：“事前配置保存路径和磁盘容量；执行前评估暂停和敏感数据；优先选择可摘除实例或复现环境。不能在所有存活实例同时生成。”

### 第三组：从“更换收集器”开始

**面试官**：“换成 ZGC 是否能够解决停顿？”

**候选人**：“先确认当前停顿确实来自 GC，并明确 JDK 版本、堆、延迟目标、吞吐和 CPU 余量。ZGC 面向低延迟，但仍需足够堆余量和 CPU，也不是完全没有停顿。”

**面试官**：“你怎样证明选择正确？”

**候选人**：“用代表性负载比较高分位停顿、请求 P99、吞吐、CPU、内存和错误率，并保持数据规模与观察时长一致。”

## 高频短问短答

### 两个对象循环引用，能够被回收吗？

能够。只要这个对象整体无法从 GC Roots 到达，循环引用不会阻止可达性分析把它们识别为可回收对象。

### `finalize()` 能否作为资源释放方案？

不能依赖它提供及时、确定的资源释放。文件、连接等外部资源应使用明确的关闭协议，例如 `try-with-resources`。

### `System.gc()` 会立刻执行吗？

它只是请求 JVM 进行回收，具体行为受收集器和配置影响，不能作为业务代码的确定释放机制。

### Young GC 是否都会停顿应用？

需要结合收集器解释。以常见 G1 Young 回收为例，对象转移发生在 STW 停顿中；并发收集器也可能保留短暂 STW 阶段。“并发”不等于整个回收过程没有停顿。

### Full GC 次数为零，说明内存健康吗？

不能。应用可能存在频繁 Young GC、原生内存增长、过大的正常工作集或尚未触发完整回收的长期引用。需要结合用户延迟、分配、回收后占用和进程总内存。

### 平均停顿很低，说明延迟目标满足吗？

不能。平均值可能掩盖少量长停顿，应该查看最大值、分位数、累计停顿和请求高分位延迟。

### 对象池一定能减少 GC 吗？

不一定。对象池可能减少特定昂贵对象的创建，也会让对象存活更久，并增加清理、并发和容量管理成本。普通小对象通常交给 JVM 管理更简单。是否使用需要通过分配数据和压测决定。

### 把局部变量设为 `null` 是否有用？

变量后续不再使用时，JIT 和作用域通常已经能够让对象失去引用。极少数超大方法或长时间执行场景可能需要具体分析，但不应把到处写 `null` 当成通用优化。

### 堆越大越好吗？

更大的堆可以容纳更大工作集并降低某些回收频率，也会增加内存成本，并可能改变停顿和故障发现时间。还要给元空间、线程栈、直接内存和系统保留余量。

### 一份堆转储能证明泄漏吗？

它能展示当时的对象和引用关系，但很难单独证明长期增长。最好结合稳定负载下的多次直方图、GC 后低点、JFR 对象增长和业务时间线。

### 为什么要记录精确 JDK 版本？

收集器默认值、日志格式、可用选项和实现都会演进。例如 JDK 24 已移除非分代 ZGC。缺少版本会让一些看似正确的回答失去适用条件。

## 一周复习时怎样安排

第一天掌握可达性、GC Roots、分代、算法与收集器的区别；第二天学习 G1 的 Young、Mixed、Full 和日志字段；第三天练习 OOM 分类、`jstat`、`jcmd`、JFR 与堆转储的用途；第四天完成短命对象与长期保留对象的对照实验；第五天用本文场景题练习两分钟回答；第六天让同伴沿工具、证据和验证连续追问；第七天只复习自己的薄弱点和项目回答。

每次练习都限制回答时间。第一轮只说三十秒，第二轮扩展到两分钟，第三轮再接受追问。这样可以避免一开口就背诵所有参数，也能让面试官选择深入方向。

## 回答前后的自检表

### 开口前先确定范围

- 面试官问的是 GC 原理、现象判断、工具使用，还是项目经历？
- 当前讨论的 JDK 版本和收集器是什么？
- 题目给出的只是相关现象，还是已经有 GC 日志与内存证据？

题目信息不足时，可以先提出一个短问题：“这里使用的是 G1 吗？能否看到 GC 日志中回收前后占用和停顿？”如果面试官不补充，就说明自己的假设，再继续回答。这样能够避免把某一种收集器的行为套到所有环境。

### 回答过程中检查证据顺序

- 是否先说了用户影响和发生时间？
- 是否区分了 Java 堆、非堆和进程总内存？
- 是否区分了分配速率与回收后存活量？
- 每个工具是否对应一个明确问题？
- 是否说明了诊断动作对运行实例的影响？

如果回答已经列出五六个工具，却没有说明先后顺序，可以立刻停下来总结：“我会先用日志和连续指标判断类型，再按分类选择 JFR、直方图或堆转储。”这比继续增加命令更清楚。

### 回答结束前检查处理与复测

- 程序修改是否针对已经找到的对象来源？
- 临时恢复和长期修改是否分开？
- JVM 配置是否建立在服务目标与测量结果之上？
- 复测是否保持流量、数据规模与观察时长可比较？
- 是否给出了延迟、停顿、回收后占用、吞吐和错误率？

面试官若没有继续追问，可以用一句话结束：“我会让每个判断都对应证据，并在同等负载下用前后数据证明修改有效。”

## 五类现象的快速判断卡

### 堆呈正常锯齿，低点稳定

对象持续创建并被正常回收。先看停顿和 CPU 是否影响用户；没有用户影响时，不必仅因曲线起伏进行调优。

### Young GC 增多，低点稳定

优先调查分配速率和短命对象。查看业务流量、大 JSON、批量集合、字符串和序列化；不能直接判断泄漏。

### 完整回收后低点持续提高

调查正常工作集增长和长期引用。先比较多次直方图，再依据影响评估是否获取堆转储，查找支配对象与 GC Roots 路径。

### Java 堆稳定，进程总内存增加

转向元空间、线程栈、直接内存、JIT 和本地库。查看容器事件、线程数、NMT 与组件指标，堆转储只能提供其中一部分线索。

### 停顿很短，累计停顿很高

单次停顿看起来不严重，但发生次数过多仍会降低吞吐并影响高分位延迟。需要同时看频率、累计时间、CPU 和请求指标。

这张判断卡只用于决定下一步证据，不能替代完整分析。真实结论仍要结合收集器、负载、日志和对象数据。

## 工具怎样与问题对应

| 工具或数据 | 主要回答的问题 | 不适合单独证明什么 |
| --- | --- | --- |
| GC 日志 | 回收类型、原因、前后占用、停顿 | 某个业务对象为什么一直存活 |
| `jstat` | 各区域占用、次数、累计时间的连续趋势 | 精确到代码的引用关系 |
| `jcmd` | 进程诊断、对象直方图、堆转储、JFR 控制 | 单个命令不能替代完整分析 |
| JFR / JMC | 一段时间内的 GC、分配、线程、锁和调用栈 | 没有开启相应事件时无法还原全部细节 |
| 堆转储 / MAT | 对象占用、支配关系、到 GC Roots 的路径 | 单份转储很难证明长期增长趋势 |
| 线程栈 | 线程状态与当时调用位置 | 单次快照很难证明持续 CPU 热点 |
| NMT 与系统指标 | 原生内存分类、进程总内存 | Java 堆中的业务引用关系 |

工具回答需要落到一句完整的话。例如不要只说“我会用 MAT”，而要说“我会在合适实例上分析堆转储，用支配树找保留量大的对象，再沿 GC Roots 引用路径确认是哪类缓存、集合或回调仍在引用它”。

## 面试中的常见失分点

1. 把回收算法和垃圾收集器混为一谈。
2. 不限定 JDK 版本与收集器，给 Full GC 下固定定义。
3. 看到 OOM 就断言存在 Java 堆泄漏。
4. 只背工具名称，不说明想获取的证据。
5. 只看 GC 次数，不看停顿、回收效果与用户延迟。
6. 看到 Full GC 后占用高就立刻断言泄漏，没有观察稳定负载下的趋势。
7. 一开始就增大堆或切换收集器，没有保存现场数据。
8. 把异步、对象池或缓存当成自动减少内存占用的方法。
9. 忽略堆转储、在线分析和全量统计对生产实例的影响。
10. 修改后只说“已经正常”，没有同等负载下的前后数据。
11. 为了显得有经验而编造生产事故，后续追问无法回答。

## 最后记住这条判断线

遇到 GC 场景题时，先问自己三件事：

1. 这是对象创建得太快，还是存活对象保留得太久？
2. 这是 Java 堆问题，还是元空间、直接内存、线程或容器总内存问题？
3. 当前要解决的是用户停顿、系统吞吐、进程容量，还是程序中的长期引用？

把这三件事判断清楚，再谈工具、代码与参数，回答就不会变成命令和 JVM 选项的堆叠。
