# 第一层：持久化模型与数据库条件更新

> 源码基线：`2e463aa290a17c01eec45d229162db3952a42e6f`
>
> 贯穿示例：运行`run-42` 已完成 `todo-1`，正在执行 `todo-2`。`todo-2` 发起沙箱任务，工具调用标识为 `tool-call-7`，尝试次数为 `1`，沙箱任务标识为 `sandbox-900`。沙箱任务需要运行十分钟，当前 Java 工作线程必须退出；结果到达后，系统还要从 `todo-2` 继续执行。

## 1. 为什么长工具需要单独的持久化模型

普通方法调用只有两种直观结果：返回值或抛出异常。长时间运行的外部工具多出第三种结果：请求已经被外部系统接受，但本地线程不应继续占有执行名额。此时，线程内的局部变量会随着方法返回而消失，后续恢复不能依赖原线程、原对象或原调用栈。

AlphaFrog 把需要跨线程保存的信息分成三类。`AgentRun` 与 `AgentRunStatus` 描述整次运行；`ToolJobAnchor` 描述某一次外部工具作业；`CompletedTodoRecord` 描述恢复时已经完成的待办前缀。`AgentRunMapper.java` 与 `AgentRunMapper.xml` 再把这些对象转换为带条件的数据库更新。事件服务向观察者说明发生过什么，但不代替数据库承担恢复资格判断。

数据库条件更新解决的是并发所有权问题。两个线程可能都读取到同一份旧状态，只有满足预期状态、操作标识、工具调用标识、尝试次数和版本号的更新才能成功。方法返回的影响行数因此是一项执行结果：返回 `1` 表示调用者仍拥有推进资格；返回 `0` 表示数据库状态已经被其他执行者改变，当前调用者应停止写入并重新读取。

## 2. `CompletedTodoRecord.java`：保存已经完成的待办前缀

### 为什么存在

恢复执行不能只记住“停在 `todo-2`”。如果系统不知道 `todo-1` 已经完成，重启后可能再次执行 `todo-1`，造成重复查询、重复计费或重复外部副作用。`CompletedTodoRecord` 提供可序列化的数据结构，让检查点携带恢复之前已经完成的待办记录。

源码路径：`agentPlatformShared/src/main/java/world/willfrog/agent/platform/dataanalysis/CompletedTodoRecord.java`。

### 从哪里开始阅读

从字段开始阅读即可。这个类没有业务判断，构造函数、读取方法和设置方法都服务于 JSON 序列化。随后阅读 `LangchainLinearRunPipelineImpl.persistToolJobCheckpoint()` 如何创建这些记录，再阅读 `LangchainLinearWorkflowExecutor.restoreCompletedTodos()` 如何恢复它们。

### 字段与输入输出

`todoId` 与 `sequence` 确认待办身份和顺序；`description` 保存原待办说明；`modelOutput`、`output` 与 `summary` 保存节点产物。类中还定义了 `toolCalls`，但基线代码没有调用 `setToolCalls()`，恢复代码也没有读取 `getToolCalls()`；当前真正延续的是锚点中的运行级 `toolCallsUsed`。`@JsonInclude(NON_NULL)` 会省略空引用字段，但整数仍保留默认值。

输入来自已经完成的 `LangchainCompletedTodo`。管线复制前六个实际使用字段，再把记录列表序列化进 `ToolJobAnchor.completedTodosJson`。恢复时，`ToolJobResumeService.parseCompletedTodos()` 先把 JSON 解析成记录列表，顺序执行器的 `restoreCompletedTodos()` 再重建可继续追加的 `LangchainCompletedTodo` 列表。代码保持 JSON 数组原顺序，不会按 `sequence` 重新排序。

### `run-42` 中发生的动作

`run-42` 在 `todo-2` 挂起时，检查点至少保存 `todo-1` 的记录。恢复执行器读取该记录后，把 `todo-1` 加入已完成集合。随后遍历原计划时跳过 `todo-1`，把外部工具终态结果注入 `todo-2`，再继续处理后面的待办。

### 失败或重启后的行为

记录为空时，恢复器从空的可变列表开始。嵌套 JSON 两次解析都失败时，恢复服务会记录警告并退化为空列表；这不会立即终止恢复，但已经完成节点的输出和数据集引用会丢失。记录中的顺序与检查点指向的挂起节点矛盾时，恢复器会返回 `resume_completed_todo_out_of_order`，防止把挂起节点或后续节点误判为已经完成。这个类只保存数据，不负责验证计划是否仍然匹配；验证发生在顺序工作流执行器。

### 与后续源码的关系

`CompletedTodoRecord` 只是一条记录，真正保存整组记录、挂起节点和外部任务身份的是 `ToolJobAnchor`。阅读完这个类后，应当转向锚点对象，理解检查点如何与外部任务终态放在同一份持久化 JSON 中。

## 3. `ToolJobAnchor.java`：保存跨线程恢复所需的外部作业事实

### 为什么存在

外部工具的创建、轮询、终态获取、容量释放和工作流恢复可能由不同线程甚至不同进程完成。仅保存 `taskId` 无法判断迟到回调属于哪次调用，也无法说明结果是否已经记账、事件是否已经发送、恢复资格是否已经被领取。`ToolJobAnchor` 把这些阶段需要共享的事实放进一份持久化对象。

源码路径：`agentPlatformShared/src/main/java/world/willfrog/agent/platform/dataanalysis/ToolJobAnchor.java`。

### 从哪里开始阅读

先按字段职责分组阅读，再阅读 `fromJson()` 与 `toJson()`。字段较多时，不宜逐个背诵；应当回答每组字段解决哪一类重复执行问题。最后对照数据库 XML 中的条件更新，确认哪些字段参与所有权判断。

### 外部作业身份字段

`operationId` 表示本轮外部操作，当前 Python 工具由运行标识、工具调用标识和尝试次数组成稳定身份；`toolCallId` 与 `attempt` 描述模型侧工具调用；`taskId` 描述沙箱侧任务；`requestFingerprint`、`canonicalCreateSpecJson` 与 `createRequestJson` 保存创建请求的稳定表示。

`anchorState` 不等同于 `AgentRunStatus`。当前分发路径会写入 `PREPARING`、`ATTACHED` 与 `PENDING`，同步快速终态会写入 `TERMINAL`。异步终态完成器不写 `anchorState=TERMINAL`，结果消费改由 `resultConsumed` 与 `resumeState` 表示。

### 工作流检查点字段

`todoId` 与 `sequence` 指向挂起节点；`completedTodosJson` 保存已完成前缀；`datasetSnapshotJson` 与 `datasetSnapshotDigest` 保存恢复时的数据集登记快照；`datasetRefsJson`、`toolCallsUsed` 与 `estimateJson` 保存后续执行需要继续使用的上下文。

`checkpointVersion` 是数据库条件更新版本。每次成功合并检查点，数据库在原值上增加一。旧工作线程携带旧版本再次写入时，条件不成立，影响行数为 `0`。

### 终态与恢复字段

`terminalStatus`、`terminalResultPreview`、`terminalRawRef`、`terminalErrorCode`、`terminalUsageJson`、`terminalAt` 与 `terminalRetryable` 保存规范化终态信封。需要注意，异步完成器为 `terminalAt` 写入本机 `Instant.now()`，它更接近完成器处理时间，不能直接描述成沙箱原始终态发生时间。`resultFetchState` 与 `resultFetchAttempts` 保存结果拉取的阶段和次数；`sandboxTerminalStatus` 保存沙箱终态。`terminalConfirmedAt` 只在沙箱已确认终态但结果体暂时缺失时设置，用作结果保留期限的起点，并非每次终态都存在。

`finalizerStep`、`finalizerError`、`usagePersisted`、`terminalEventEmitted` 与 `resultConsumed` 让终态完成器能够按步骤重入。`resumeState`、`resumeToken`、`resumeLeaseVersion` 与 `resumeClaimedAt` 表示恢复资格从 `READY` 到 `LAUNCHING` 再到 `CONSUMED` 的交接过程。`autoResume` 与 `runDisposition` 记录用户控制或检查点失败后的处理意图。

`reservationJson` 保存外部容量预留；`nextPollAt` 与 `timeoutAt` 保存轮询和超时计划。外部容量与智能体工作线程名额属于两套资源，不能混为同一个计数。

### 序列化方法

`fromJson(String)` 遇到损坏 JSON 会抛出 `IllegalArgumentException`。它没有静默创建空锚点，因为空对象会丢失所有权身份。`toJson()` 遇到序列化失败也会抛出异常，阻止调用者把空 JSON 写入数据库。

### `run-42` 中发生的动作

`run-42` 创建外部任务前写入 `PREPARING` 锚点，随后保存 `sandbox-900`。快速等待窗口结束时，工具分发先把 `PENDING` 锚点和运行状态 `WAITING_TOOL_JOB` 写入数据库。挂起异常传播到运行管线后，另一条条件更新才合并 `todo-2`、已完成的 `todo-1`、数据集快照和工具调用计数。沙箱终态到达后，完成器继续更新终态信封、容量释放、记账、事件、运行状态和恢复资格。恢复器凭 `resumeToken` 与 `resumeLeaseVersion` 领取新一轮执行权。

### 失败或重启后的行为

进程重启后，协调器从数据库重新读取锚点，不依赖旧线程。不同语义方法检查各自需要的预期条件；较宽的 `updateToolJobAnchor()` 与 `updateToolJobAnchorAndStatus()` 没有完整的操作身份和版本保护。若 JSON 已损坏，读取会明确失败，避免在缺少身份保护的情况下继续。若恢复租约已经被其他进程推进，旧进程后续用于接受交接、推进锚点或清理锚点的令牌与版本条件更新会返回 `0`。

这组条件更新并未覆盖旧恢复任务的整个执行过程。恢复 `Runnable` 开始运行时只重新读取 `AgentRun`，没有把 `ToolJobResumeContext` 中的令牌与版本和最新锚点再次比较。跨进程的旧任务若仍在另一进程队列中，可能在租约过期并被新进程改写后继续执行模型或工具；后续交接与清理会被条件更新拒绝，但已经发生的外部副作用不会因此撤销。

### 与后续源码的关系

锚点最终保存在 `AgentRun.toolJobAnchorJson` 中。阅读 `AgentRun` 可以把外部作业的局部状态放回整次运行的生命周期中。

## 4. `AgentRun.java`：把运行状态、计划、快照与锚点放在同一行

### 为什么存在

恢复系统需要一个数据库聚合对象，把运行身份、用户身份、运行状态、计划、结果快照、过期时间和工具锚点关联起来。`AgentRun` 对应 `alphafrog_agent_run` 表的一行，是 MyBatis 读写的实体对象。

源码路径：`agentPlatformShared/src/main/java/world/willfrog/agent/platform/entity/AgentRun.java`。

### 从哪里开始阅读

先阅读 `id`、`userId` 与 `status`，确认对象代表哪次运行以及当前阶段。再阅读 `planJson`、`snapshotJson` 和 `toolJobAnchorJson`，理解三份 JSON 的职责。最后阅读时间与统计字段，区分恢复事实和列表页展示数据。

### 字段与状态变化

`status` 保存整次运行阶段；`currentStep` 与 `maxSteps` 保存进度；`planJson` 保存规划结果；`snapshotJson` 保存运行结果或失败快照；`lastError` 保存最近错误；`ttlExpiresAt`、`startedAt`、`updatedAt` 与 `completedAt` 保存生命周期时间。

`ext` 保存运行级配置 JSON。`toolJobAnchorJson` 保存 `ToolJobAnchor` 的完整 JSON。`durationMs`、`totalTokens` 与 `toolCalls` 主要供列表查询映射统计摘要，它们不参与外部工具恢复所有权判断。

### `run-42` 中发生的动作

`run-42` 开始时可能处于 `RECEIVED`。`executeRun()` 在调用规划器之前先把状态更新为 `EXECUTING` 并发送执行开始事件，随后才生成计划。`todo-2` 完成长工具责任交接后，同一行中的 `status` 变成 `WAITING_TOOL_JOB`，`toolJobAnchorJson` 先保存外部作业，再由管线合并工作流检查点。完成器随后把状态条件更新为 `RECEIVED`，恢复服务再为该行领取 `LAUNCHING` 资格。

### 失败或重启后的行为

实体类不实施恢复，也不保证字段之间一致。安全性来自同一条 SQL 同时更新锚点与状态，以及后续更新的条件判断。只在 Java 对象中调用设置方法不会产生数据库效果。重启后必须重新查询数据库，不能继续使用进程退出前的旧对象。

### 与后续源码的关系

`AgentRunMapper.java` 定义哪些数据库操作可以读取或推进这行记录。它也是理解“影响行数为什么属于控制信号”的入口。

## 5. `AgentRunMapper.java`：定义数据库仲裁接口

### 为什么存在

服务层不应散落手写 SQL，也不能把所有更新都写成“按运行标识直接覆盖”。`AgentRunMapper` 把普通查询、状态更新、工具锚点推进、检查点合并和恢复租约声明整理为明确方法。方法返回的整数让调用者判断自己是否仍拥有写入资格。

源码路径：`agentPlatformShared/src/main/java/world/willfrog/agent/platform/mapper/AgentRunMapper.java`。

### 从哪里开始阅读

普通的 `insert()`、`findById()`、`findByIdAndUser()` 与 `updateSnapshot()` 可以快速浏览。长工具部分从注释“长工具上下文切换”开始详细阅读，重点关注每个方法的预期条件，以及返回 `0` 后调用者应当停止的语义。

### 初次分发与活跃作业推进

`claimPreparingToolJobAnchor()` 只在运行状态匹配且锚点为空时写入首个 `PREPARING`。`updateActiveToolJobAnchor()` 额外匹配 `expectedOperationId`，让旧操作的迟到写入失效。`updateToolJobAnchorAndStatusByOperation()` 在同一条语句中推进锚点并转换运行状态。`clearActiveToolJobAnchor()` 也要求操作标识匹配，旧清理动作不能删除新锚点。

接口中也保留 `updateToolJobAnchor()` 与 `updateToolJobAnchorAndStatus()` 两个较宽的入口，它们只匹配运行状态，不匹配操作标识或版本。不能把映射层中的每个锚点更新都描述成完整身份条件更新；调用方应优先依赖语义更窄的方法。

### 检查点与失败所有权

`updateToolJobCheckpoint()` 匹配运行状态、操作标识、工具调用标识、尝试次数、沙箱任务标识和检查点版本，只合并恢复白名单字段并增加版本。`markToolJobCheckpointFailed()` 在完整检查点无法写入时，尝试冻结 `CHECKPOINT_FAILED` 处置。`markToolJobCheckpointFailurePending()` 将完整失败请求编码进 `last_error`，供后续协调器重新处理；`clearToolJobCheckpointFailurePending()` 只清除仍与当前标记相同的值。

检查点失败恢复服务可能返回 `FAILURE_OWNED`、`HEALTHY_CHECKPOINT` 或 `UNOWNED`。`UNOWNED` 表示当前调用者没有取得可靠处理资格，它不等价于已经写入 `FAILED`。教程和面试回答都应保留这项限制。

### 终态恢复资格

`casUpdateStatus()` 只在旧状态匹配时转换运行状态。`listActiveToolJobAnchors()` 与 `listResumeReadyAnchors()` 提供两类数据库扫描。`casUpdateAnchorResumeState()` 匹配运行状态、旧恢复阶段、令牌和租约版本。`clearToolJobAnchorWithToken()` 也要求令牌和版本匹配，防止旧恢复者删除新执行者的上下文。

### `run-42` 中发生的动作

`run-42` 先通过 `claimPreparingToolJobAnchor()` 取得空锚点，再通过活跃作业更新保存 `sandbox-900`。挂起时，`updateToolJobAnchorAndStatusByOperation()` 将状态从 `EXECUTING` 修改为 `WAITING_TOOL_JOB`。管线再调用 `updateToolJobCheckpoint()` 保存 `todo-2` 和 `todo-1` 前缀。终态完成器和恢复服务继续调用状态条件更新与恢复租约条件更新。

### 失败或重启后的行为

任一条件更新返回 `0` 时，调用者应当重新读取数据库或停止当前步骤。数据库扫描能够重新发现满足查询条件的作业，但不能概括为“任何中间状态都一定会被启动扫描找到”。实际可发现范围由 XML 中两条查询的状态集合和 JSON 条件决定。

### 与后续源码的关系

接口参数中频繁出现 `AgentRunStatus`。理解状态枚举后，才能解释每条条件更新为什么期待 `EXECUTING`、`WAITING_TOOL_JOB` 或 `RECEIVED`。

## 6. `AgentRunStatus.java`：区分执行、人工等待和外部工具等待

### 为什么存在

整次运行会经历接收、规划、执行、总结和终态，也可能因人工暂停或外部工具而等待。若把所有等待都压成一个状态，执行守卫无法判断旧线程为何退出，控制服务也无法选择正确恢复入口。

源码路径：`agentPlatformShared/src/main/java/world/willfrog/agent/platform/model/AgentRunStatus.java`。

### 从哪里开始阅读

先把状态分为四组：进入执行的 `RECEIVED/PLANNING/EXECUTING/SUMMARIZING`，人工暂停的 `WAITING`，外部作业等待的 `WAITING_TOOL_JOB`，以及 `COMPLETED/PARTIAL/FAILED/CANCELED/EXPIRED` 等终态。随后阅读 `WAITING_TOOL_JOB` 上方注释，确认终态完成后不会直接改回 `EXECUTING`。

### 状态变化

外部工具责任交接成功后，运行从 `EXECUTING` 转为 `WAITING_TOOL_JOB`。工具终态完成器先保存结果与恢复信息，随后将运行条件更新为 `RECEIVED`。恢复服务将锚点的 `resumeState` 从 `READY` 声明为 `LAUNCHING`，重新排队取得工作线程后继续执行。

人工 `WAITING` 使用人工恢复入口。`WAITING_TOOL_JOB` 使用锚点、终态完成器和恢复租约。二者都会让旧线程停止，但恢复资格来源不同。

### `run-42` 中发生的动作

`run-42` 在 `todo-2` 发起长工具前处于 `EXECUTING`。责任交接完成后处于 `WAITING_TOOL_JOB`，此时读取接口应向前端展示外部工具等待。沙箱结果完成必要处理后，运行变为 `RECEIVED`，新工作线程从原计划继续。

### 失败或重启后的行为

`WAITING_TOOL_JOB` 让启动恢复扫描能够在部分阶段找到活跃锚点。当前人工暂停实现会把 `WAITING_TOOL_JOB` 覆盖为 `WAITING`，却不会同步修改锚点的 `autoResume` 和 `runDisposition`；这会破坏完成器期待的状态条件，应当作为当前限制说明。状态枚举本身不修复这项行为。

### 与后续源码的关系

状态说明当前运行处于哪一阶段，事件说明观察者看见了哪些动作。`AgentEventService` 展示事件为何只能承担通知和审计职责。

## 7. `AgentEventService.java`：提供事件序列，不承担恢复仲裁

### 为什么存在

用户界面、调试工具和审计程序需要知道运行何时接收、何时挂起、何时恢复以及何时失败。直接轮询主表只能看到当前状态，无法重建动作顺序。`AgentEventService` 提供按序号追加和读取的事件流。

源码路径：`agentPlatformShared/src/main/java/world/willfrog/agent/platform/service/AgentEventService.java`。

### 从哪里开始阅读

先阅读类注释，确认事件默认写入 Redis 有序集合，并在过渡期双写 PostgreSQL。再阅读 `createRun()`、`isRunnable()`、`append()`、`appendOnce()` 和各类读取方法。大量 `extractXxx()` 方法属于运行配置解析，可以放到后面阅读。

### 创建、判断与追加

`createRun()` 创建运行标识，组装 `ext`，写入状态为 `RECEIVED` 的 `AgentRun`，随后追加 `RUN_RECEIVED`。`isRunnable()` 读取数据库运行，拒绝 `CANCELED`、`EXPIRED`、`WAITING` 与 `WAITING_TOOL_JOB`，也会检查过期时间。

`append()` 生成事件序号、规范化载荷，先写入 Redis 事件存储，再写入 PostgreSQL，最后发布实时通知。`appendOnce()` 先通过 PostgreSQL 的唯一去重插入取得事件所有权；重复调用读取已有数据库事件并补充 Redis，不会再次发布实时通知。事件载荷过长时，`normalizePayloadJson()` 会保存摘要，避免单条事件无限膨胀。

### `run-42` 中发生的动作

`run-42` 建立检查点之后才追加工具挂起事件。这个顺序保证观察者读取到挂起事件时，数据库已经保存可恢复上下文。恢复成功后，管线使用带令牌和租约版本的去重键追加 `WORKFLOW_RESUMED`。重复恢复尝试不会依靠普通事件来决定执行权。

### 失败或重启后的行为

事件读取优先使用 Redis；只有 `eventRedisStore.hasEvents(runId)` 为假时才回退数据库，两端结果不会合并。Redis 的序号和实时发布有助于观察，但数据库条件更新仍是锚点和恢复租约的裁决依据。事件写入失败不能被解释为外部作业没有发生，事件写入成功也不能证明当前调用者仍拥有恢复资格。

序号键使用 `ttlMinutes`，默认值与类注释中的事件七天 TTL 不同。序号键过期或丢失后会从 `1` 重新计数，代码不会先读取数据库最大序号；数据库若保留旧事件，`(run_id, seq)` 唯一约束可能拒绝新事件。终态完成器可能停在事件步骤等待重试，这也是当前实现需要继续修复的重启风险。

### 与后续源码的关系

Java 接口只声明数据库操作，真正的条件位于 `AgentRunMapper.xml`。阅读 XML 可以把“返回 `0` 表示失去资格”落实到具体 `WHERE` 条件。

## 8. `AgentRunMapper.xml`：把所有权条件写进同一条 SQL

### 为什么存在

Java 层的“读取后判断再更新”会在读取和写入之间留下并发窗口。XML 将预期状态、操作身份和版本号直接放进 `UPDATE ... WHERE ...`，让 PostgreSQL 在一条语句中判断当前值是否仍然匹配。

源码路径：`agentPlatformShared/src/main/resources/mapper/AgentRunMapper.xml`。

### 从哪里开始阅读

先浏览 `AgentRunResultMap` 和普通查询，确认 JSONB 字段如何映射为文本。长工具部分从 `updateToolJobAnchor` 开始。阅读每条更新时，把 `SET` 与 `WHERE` 分开：`SET` 说明准备写入什么，`WHERE` 说明调用者凭什么拥有写入资格。

### 初次声明与操作身份

`claimPreparingToolJobAnchor` 要求运行状态匹配，并要求锚点为空或 `{}`。并发工作线程中只有一个能够影响一行。`updateActiveToolJobAnchor`、`updateToolJobAnchorAndStatusByOperation` 与 `clearActiveToolJobAnchor` 都匹配 `operationId`，防止旧回调或旧清理动作覆盖新操作。

### 检查点合并

`updateToolJobCheckpoint` 使用 JSONB 合并，只修改 `checkpointVersion`、待办位置、已完成待办、数据集快照、数据集引用、工具调用计数和估算信息。它不会整对象覆盖终态、容量预留或完成器字段。`WHERE` 同时匹配运行状态、操作标识、工具调用标识、尝试次数、任务标识和旧版本。

PostgreSQL 当前文档说明，在默认 `Read Committed` 隔离级别下，并发更新会等待前一更新完成，并对更新后的行重新判断 `WHERE` 条件。这正是条件更新能够拒绝迟到执行者的数据库基础。业务层仍需检查影响行数，不能把没有异常等同于更新成功。

### 两类扫描及其当前遗漏

`listActiveToolJobAnchors` 只扫描状态位于 `EXECUTING`、`WAITING_TOOL_JOB`、`WAITING`、`CANCELED` 且锚点非空的记录。`listResumeReadyAnchors` 只扫描状态为 `RECEIVED` 且 `resumeState` 为 `READY` 或 `LAUNCHING` 的记录。

由此存在两个当前遗漏。第一，完成器已经将状态修改为 `RECEIVED`，但还没将 `resumeState` 写入为 `READY` 时进程退出；若 Redis 索引也丢失，两条数据库扫描都不匹配。第二，运行已经进入 `COMPLETED`、`PARTIAL` 或 `FAILED`，锚点仍残留 `LAUNCHING` 时，两条扫描同样不匹配。教程必须将它们写成现有限制，不能承诺下一次启动一定恢复所有中间状态。

### `run-42` 中发生的动作

`run-42` 的首个 `PREPARING` 更新要求空锚点。保存 `sandbox-900` 时要求相同操作标识。挂起时，一条 SQL 同时写入下一版锚点并将状态从 `EXECUTING` 修改为 `WAITING_TOOL_JOB`。检查点合并要求旧版本匹配。恢复服务领取资格时，`resumeState`、`resumeToken` 和 `resumeLeaseVersion` 必须全部匹配。

### 失败或重启后的行为

进程退出后，数据库保留已提交的最后一步。协调器只能重新进入当前查询能够发现的状态。某条条件更新返回 `0` 时，旧执行者不能退化为无条件更新。若采用更高事务隔离级别，还需准备处理序列化失败并重试整个事务；当前教程只描述这组单语句条件更新的代码事实。

### 与后续源码的关系

SQL 提供持久化能力，工具模块不应直接依赖 MyBatis 细节。`PythonSandboxDispatchStore` 通过四个语义化方法把工具分发和数据库实现分开。

## 9. `PythonSandboxDispatchStore.java`：为工具模块提供持久分发接口

### 为什么存在

Python 沙箱工具位于共享工具模块，数据库映射位于平台共享模块。若工具直接依赖运行服务的实现类，会产生不合适的模块依赖。`PythonSandboxDispatchStore` 把分发过程压缩成四个业务动作，由服务模块提供具体实现。

源码路径：`agentPlatformShared/src/main/java/world/willfrog/agent/platform/dataanalysis/PythonSandboxDispatchStore.java`。

### 从哪里开始阅读

按外部任务生命周期阅读四个方法：创建前调用 `persistPreparing()`，取得沙箱任务标识后调用 `persistAttached()`，确认任务仍在后台运行时调用 `transferToPending()`，创建失败或同步结束需要清理活跃锚点时调用 `clearActive()`。

### 方法、输入与输出

基线实现对四个方法还有明确前置条件。`persistPreparing(String runId, ToolJobAnchor anchor)` 要求 `anchorState=PREPARING`、运行状态为 `EXECUTING`、旧锚点为空。`persistAttached(...)` 要求 `anchorState` 为 `ATTACHED` 或同步快速路径的 `TERMINAL`、运行状态为 `EXECUTING`、操作标识匹配。`transferToPending(...)` 要求 `anchorState=PENDING`、运行状态为 `EXECUTING`、操作标识匹配，并以原子方式将运行修改为 `WAITING_TOOL_JOB`。`clearActive(String runId, String operationId)` 要求运行仍为 `EXECUTING` 且操作标识匹配。

四个方法都返回布尔值。`true` 表示数据库接受了当前动作；`false` 表示预期条件不成立。特别是 `transferToPending()`，只有返回 `true`，当前工作线程才具备退出条件。

### `run-42` 中发生的动作

`run-42` 在调用沙箱创建接口之前执行 `persistPreparing()`。收到 `sandbox-900` 后执行 `persistAttached()`。快速等待窗口结束仍无终态时，执行 `transferToPending()`；成功后，工具抛出结构化挂起异常，让上层保存工作流检查点并退出当前工作线程。

### 失败或重启后的行为

创建请求超时并不说明沙箱没有接受任务，锚点中的稳定请求身份为后续重查和幂等处理提供依据。若 `persistPreparing()` 返回 `false`，工具不能继续创建任务。基线工具在首次 `ATTACHED` 写入处没有检查 `persistAttached()` 的返回值，但后续待处理转交仍会使用操作标识执行数据库条件更新；教程不能将首次附着描述成调用方已经检查成功。若 `transferToPending()` 返回 `false`，工具不能假装责任已经交给后台协调器。重启后的轮询与完成处理由其他服务读取数据库锚点继续。

### 与后续源码的关系

持久责任交接成功后，工具需要让 LangChain4j 调用栈停止。`ExternalToolJobPendingException` 携带最小稳定身份，将“后台仍在运行”传给工作流层。

## 10. `ExternalToolJobPendingException.java`：把后台等待表示为结构化控制信号

### 为什么存在

外部作业已经被接受时，返回普通字符串会让模型继续推理，抛出普通工具异常又会被当成失败文本交给模型修复。两种处理都无法表达“当前节点暂停、工作线程退出、以后恢复”。`ExternalToolJobPendingException` 提供独立控制信号。

源码路径：`agentPlatformShared/src/main/java/world/willfrog/agent/platform/dataanalysis/ExternalToolJobPendingException.java`。

### 从哪里开始阅读

先阅读三个只读字段 `runId`、`toolCallId`、`attempt`，再阅读构造函数和读取方法。随后转向 `LangchainTerminalToolErrorHandler` 与 `LangchainTodoNodeExecutor.findPending()`，确认异常不会被压成普通错误字符串。

### 输入与输出

构造函数接收运行标识、工具调用标识、尝试次数和消息。消息供日志与异常传播使用；三个字段负责跨内存层传播和事件诊断。它们不会被运行管线用来构造或校验数据库检查点身份。这个异常不携带完整 `ToolJobAnchor`，上层会按运行标识重新读取数据库中的最新锚点。

### `run-42` 中发生的动作

`transferToPending()` 成功后，工具抛出包含 `run-42`、`tool-call-7` 和尝试次数 `1` 的异常。终态错误处理器沿异常原因保留它，待办节点执行器再把它转换为 `LangchainTodoNodeResult.suspended(...)`。三元身份会进入节点结果和工作流结果，并用于挂起事件；管线构造检查点时会重新读取数据库锚点，以其中的操作、工具、尝试、沙箱任务和版本作为检查点身份。`pendingRunId` 传播到工作流结果后没有被管线读取，当前实现也没有显式交叉校验异常身份与锚点身份。

### 失败或重启后的行为

异常只存在于当前调用栈，进程退出后不会保留。抛出之前，工具责任交接已经把 `PENDING` 锚点和 `WAITING_TOOL_JOB` 写入数据库；完整工作流检查点仍要等待异常传播到运行管线后另行条件合并。若前一步责任交接失败就抛出异常，工作流可能退出且没有可靠外部作业所有者；若完整检查点写入失败，管线还要取得健康检查点或明确失败处理资格后才能结束当前处理。

### 与第二层的连接

第二层从这个异常如何穿过工具异常处理、待办节点结果、工作流结果、管线和调度器展开。阅读重点从“保存了什么”转为“挂起信号如何让当前工作线程安全退出，并在终态到达后重新排队”。

## 11. `run-42` 的第一层时序

```text
AgentRun.status = EXECUTING，anchor 为空
  ↓ claimPreparingToolJobAnchor
anchor = PREPARING，operationId 已固定
  ↓ 沙箱接受请求
persistAttached 保存 sandbox-900
  ↓ 快速等待窗口结束
transferToPending 原子写 anchor 并改状态为 WAITING_TOOL_JOB
  ↓ 顺序工作流生成 suspended 结果
updateToolJobCheckpoint 保存 todo-1 前缀与 todo-2 位置，版本加一
  ↓ 当前工作线程退出
终态完成器分步保存终态、释放容量、记账、发事件、准备恢复令牌
  ↓运行状态进入 RECEIVED 且 resumeState=READY
恢复服务使用 token 与 lease version 领取 LAUNCHING
```

这条时序中，事件负责说明动作，数据库条件更新负责决定谁能推进。工作线程可以消失，运行状态和锚点仍然留在 PostgreSQL。Redis 能够提供快速索引和事件读取，但教程不能把 Redis 索引描述为唯一事实来源。

## 12. 面试表达

如果面试官问为什么需要 `ToolJobAnchor`，第一句可以回答：长工具运行时间超过单个 Java 工作线程应当占用的时间，所以系统把外部任务身份、工作流检查点、终态处理进度和恢复租约保存到数据库，让旧线程退出后仍能继续。

随后说明两项设计。第一，`WAITING_TOOL_JOB` 将外部等待与人工暂停区分。第二，映射层使用状态、操作标识、任务标识、尝试次数和版本号执行条件更新，影响行数为 `0` 时调用者停止推进。最后落到项目事实：当前实现能够恢复 `LINEAR` 工作流的一次长工具等待，但仍有扫描遗漏、人工暂停覆盖等待状态和第二次长任务无法再次挂起等限制。

遇到“数据库写了一半怎么办”的压力追问，可以按以下顺序回答：承认当前实现仍有两个启动扫描遗漏；说明已提交步骤会保留在数据库，完成器与恢复器按步骤重入；再指出只有当前扫描条件能够发现的状态才会自动重试，不能把现状描述成任意断点都能恢复。
