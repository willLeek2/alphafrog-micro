# 第六层：用户控制与读取视图

这一层讨论用户怎样取消、暂停、恢复或删除运行，以及客户端怎样读取状态、事件和结果。控制服务会同时接触 PostgreSQL、Redis、可观测快照、事件和费用结算，任何“按钮语义”都必须与长工具锚点的持久责任一致。读取服务则以 PostgreSQL运行记录为入口，补充事件、计划、观测摘要和费用视图。当前实现有四个需要主动说明的缺口：暂停会覆盖长工具等待状态，删除方法的运行中集合不含 `WAITING_TOOL_JOB`，计划覆盖值保存后没有被主管线消费，单写者守卫只是空值检查。

## `LangchainRunControlService.java`

完整路径：`agentLangchainService/src/main/java/world/willfrog/agentlangchain/facade/LangchainRunControlService.java`

### 为什么存在与怎样阅读

用户控制不是简单地停止线程。运行可能正在执行模型、等待普通工具，也可能已经释放智能体工作线程并等待沙箱。控制服务需要先保留外部作业的释放责任，再修改用户可见状态。

从 `cancelRun()` 开始阅读。它先通过 `requireWritableRun()` 取得运行。若存在 `operationId` 非空的工具锚点，会先把 `autoResume=false` 与 `runDisposition=CANCELED` 写入数据库；写入失败时取消请求失败关闭，避免提前覆盖 `WAITING_TOOL_JOB` 后让容量无人释放。随后 Redis 写入 `CANCELING`，线程休眠 200 毫秒，让仍在执行的执行守卫有机会观察该状态。休眠期间感知的是 `CANCELING`，不是 `CANCELED`。

观测数据刷新后，有活跃锚点的运行只更新快照，数据库状态暂时保留原值；终态完成器释放容量后才写入 `CANCELED`。没有活跃锚点时，控制服务直接更新快照、状态和中断 TTL。最后追加取消事件、将 Redis 状态修改为 `CANCELED`，并异步触发费用结算。取消与暂停路径中的多处快照或状态数据库映射方法返回值没有检查，数据库更新也没有与事件、Redis 和费用结算放进同一事务；数据库写入失败后，后续事件发布、Redis 状态修改或结算调度仍可能继续。

源码注释把失败与取消描述为不可逆终态，`isTerminal()` 也把 `FAILED`、`CANCELED` 都视为终态；公开方法 `resumeRun()` 却明确接受 `FAILED`、`CANCELED` 和 `WAITING`，重置后再次启动。因此当前实现对失败和取消都有“终态判断不可逆、恢复入口又允许重启”的语义矛盾。教程应陈述代码事实，不能只复述注释。

### 暂停、恢复与计划覆盖

`pauseRun()` 直接将数据库和 Redis 状态修改为 `WAITING`，保存观测快照并发布 `PAUSED`。它没有读取或修改工具锚点。对于普通执行，这提供了可恢复的用户状态；对于 `WAITING_TOOL_JOB`，它会覆盖完成器需要的数据库前置状态，却保留 `autoResume=true`。协调器可能仍尝试自动恢复，完成器写入又因期望 `WAITING_TOOL_JOB` 而失败。当前代码没有实现长工具暂停的完整语义。

`resumeRun()` 对 `EXPIRED` 抛出异常，对其他非 `FAILED/CANCELED/WAITING` 状态直接返回。带 `planOverrideJson` 时，它执行 `clearTasks()` 和 `storePlanOverride()`，随后 `resetForResume()`、发布 `WORKFLOW_RESUMED`、将 Redis 状态修改为 `RECEIVED` 并调用 `pipeline.launchAsync()`。主运行管线没有读取 `isPlanOverride()` 来跳过规划器，因此“计划覆盖值已写入 Redis”成立，“本次执行一定采用计划覆盖值”没有代码支撑。

### 删除、`run-42` 与失败行为

`deleteRun()` 只拒绝 `RECEIVED/PLANNING/EXECUTING/SUMMARIZING`。`isRunning()` 不含 `WAITING_TOOL_JOB`，所以 `run-42` 等待 `task-99` 时能够通过删除检查。数据库运行记录删除后，锚点随行消失，后台外部任务和容量预留失去正常终态处理入口。这是当前保护缺口，不能把方法概括为“仅允许安全的非运行状态删除”。

用户在 `run-42` 等待长工具时点击取消，安全路径是先保存 `CANCELED` 处置方式，再显示取消，最后由协调器和完成器等待真实沙箱终态、释放容量并写入数据库终态。若在事件之后、费用结算调度之前崩溃，读取路径不会自动补发结算。若在锚点更新后、Redis 写入前崩溃，数据库中的 `autoResume=false` 仍能让后续协调器执行取消收尾。

## `LangchainRunReadService.java`

完整路径：`agentLangchainService/src/main/java/world/willfrog/agentlangchain/facade/LangchainRunReadService.java`

### 为什么存在与怎样阅读

客户端需要不同粒度的读取：运行列表展示摘要，事件接口按序号补洞，状态接口高频返回轻量视图，结果接口返回最终答案与完整观测，快照接口按分段读取大对象。将这些读取集中到服务中，可以复用用户归属检查、过期处理和字段组装，同时避免每个调用方自行解释运行状态。

建议先阅读 `requireRun()` 与 `markExpiredIfNeeded()`，再阅读 `listRuns()`、`listEvents()`、`getStatus()`、`getResult()` 和快照分段方法。单个运行与管理员读取会通过 `requireRun()` 或 `requireRunForAdmin()` 触发 `markExpiredIfNeeded()`：普通状态更新写入 `EXPIRED`，随后追加 `RUN_EXPIRED` 并刷新 Redis。状态更新没有旧状态条件，事件也没有去重键；并发读取可能重复追加 `RUN_EXPIRED`。该写入由某次单运行读取触发，后台定时器没有提供这项保证。

### 运行列表、事件游标与状态摘要

`listRuns()` 负责分页和状态筛选，列表项主要使用数据库运行记录及快照中的统计摘要。列表遇到应过期记录时只将响应中的展示状态修改为 `EXPIRED`，不会写入数据库、事件或 Redis。它适合历史页，不替代单个运行的完整状态查询。`listEvents()` 把负数 `afterSeq` 归零，按游标读取后续事件并计算下一游标；调用方可保存 `nextAfterSeq`，断线后继续拉取，而无需每次下载全部事件。

`getStatus()` 返回运行状态、推断阶段、最近事件、计划进度、观测摘要、费用和已用时间。它只加载观测摘要，不拉取完整追踪数据。`resolvePhase()` 将 `WAITING_TOOL_JOB` 单独暴露，避免前端误显示为人工暂停。轮询频率由客户端决定；若示例假设每 3 秒调用一次，应明确它是场景参数，不是读取服务的代码保证。

### 最终结果、快照分段与辅助查询

`getResult()` 从 `snapshotJson` 提取答案，加载完整观测视图，并通过费用服务计算总消耗。它适合终态详情页，响应体通常比 `getStatus()` 大。快照元数据与分段读取方法让客户端按分段获取大对象，避免把所有内容塞进一次状态轮询。配置、模型和额度查询属于同一服务的辅助读取，但不参与长工具恢复资格判断。

### `run-42`、访问守卫与失败行为

假设客户端每 3 秒读取 `run-42`，`getStatus()` 从数据库看到 `WAITING_TOOL_JOB`，结合最近事件与计划构造轻量响应，并把阶段显示为 `WAITING_TOOL_JOB`。沙箱终态被消费、运行最终进入 `COMPLETED` 后，客户端再调用 `getResult()` 取得答案与完整观测。

`requireReadableRun()` 和 `requireWritableRun()` 会调用 `LangchainSingleWriterGuard`。当前守卫的两个方法只检查传入运行是否为空，然后原样返回；它没有验证所有者、租约、实例路由或缓存新旧。类名表达了未来职责，但当前代码不能证明已有单写者隔离。数据库不可用、运行不存在或用户不匹配时，读取会抛出异常；Redis 计划或观测辅助数据缺失时，各方法按自己的空值与数据库快照回退规则组装响应。

## 面试表达与配套阅读

面试官问“取消、暂停和恢复有什么区别”时，可以先按已实现路径回答：活跃长工具的取消路径先冻结 `runDisposition`，保留 `WAITING_TOOL_JOB` 直到容量释放；暂停路径直接写入 `WAITING`；恢复路径重置为 `RECEIVED` 并启动新任务。随后主动指出当前不一致：`resumeRun()` 允许 `CANCELED`，`pauseRun()` 未处理活跃锚点，计划覆盖值没有被主管线消费，`deleteRun()` 也没有把 `WAITING_TOOL_JOB` 视为运行中。

读取侧可以回答为五类契约：列表分页、事件游标、轻量状态、完整结果、快照分段。`getStatus()` 适合轮询，`getResult()` 适合终态详情；`WAITING_TOOL_JOB` 的显示不会触发恢复，真正恢复资格仍来自数据库锚点的 `resumeState`、`resumeToken` 和 `resumeLeaseVersion`。

配套资料可阅读 PostgreSQL 事务隔离文档 <https://www.postgresql.org/docs/current/transaction-iso.html> 和 Java `ThreadPoolExecutor` 文档 <https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/concurrent/ThreadPoolExecutor.html>。前者帮助理解控制与完成器的条件更新，后者帮助区分线程中断、任务排队与业务状态；项目行为仍以本章源码为准。
