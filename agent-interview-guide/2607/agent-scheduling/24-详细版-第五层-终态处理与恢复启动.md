# 第五层：终态处理与恢复启动

这一层从沙箱已经结束讲起，回答两个问题：后台协调器怎样把外部结果安全地带回智能体运行，以及新工作线程怎样取得恢复资格。阅读时要把 PostgreSQL 锚点视为持久事实，把 Redis 视为轮询和唤醒的辅助结构。当前代码实现了分步终态处理、容量释放、用量与事件记录、恢复租约和重新排队，同时保留了两个数据库扫描遗漏和跨进程旧排队任务风险。教程会把这些限制与已经实现的保证放在同一处说明。

贯穿示例使用 `run-42`。它在 `todo-2` 调用 Python 沙箱，外部任务编号为 `task-99`，工具调用编号为 `call-7`，尝试次数为 `1`。旧智能体工作线程已经退出，运行处于 `WAITING_TOOL_JOB`，完整工作流检查点和容量预留都保存在数据库锚点中。

## `ToolJobResultValidator.java`

完整路径：`agentLangchainService/src/main/java/world/willfrog/agentlangchain/tooljob/ToolJobResultValidator.java`

### 为什么存在与怎样阅读

沙箱的状态查询与结果查询不是同一个响应。网络延迟、服务端保留期或迟到响应都可能让调用方拿到空结果或错配结果。若后台协调器仅凭“状态已经成功”就把结果注入 `todo-2`，另一个任务的数据可能进入 `run-42`。这个包级工具类把在线协调器与启动恢复共同需要的响应检查收在一个入口中，但它不提供运行级或操作级身份校验。

先阅读唯一的静态方法 `validate(requestedTaskId, runId, resp, expectedStatus)`。方法把检查委托给 `SandboxTerminalResultValidator`。它要求响应非空、响应 `taskId` 非空且等于请求值、响应 `status` 非空且等于预期值；`SUCCEEDED` 至少包含 `stdout` 或 `datasetDir`，`FAILED/CANCELED` 至少包含 `error` 或 `stderr`。`runId` 只进入日志，不参与比较。方法也不检查 `operationId`、`toolCallId`、`attempt`、`retryable` 或 `resourceUsage`。

### `run-42` 中的动作与失败处理

协调器先确认 `task-99` 为 `SUCCEEDED`，再请求结果并调用 `validate("task-99", "run-42", resp, "SUCCEEDED")`。只有通过上述窄检查的非空响应才会进入终态完成器。返回 `null` 不表示运行已经失败，调用方需要保存下一次轮询时间并稍后重试。返回非空也只证明任务编号、状态与最小结果字段符合要求，不能证明响应属于 `run-42/call-7/attempt=1` 这组完整操作身份。

校验器没有持久状态。进程重启后，同一数据库锚点会驱动下一次查询与校验。通过校验的响应随后交给 `ToolJobFinalizer`；校验失败的响应不能绕过完成器直接写入工作流。

## `ToolJobFinalizer.java`

完整路径：`agentLangchainService/src/main/java/world/willfrog/agentlangchain/tooljob/ToolJobFinalizer.java`

### 为什么存在与怎样阅读

外部任务结束后仍有多项必须完成的动作：保存终态信封、释放沙箱容量、记录资源用量、发布终态事件、把运行改回可执行状态、生成恢复资格。这些动作跨越数据库、容量服务、事件服务和 Redis，无法由一个事务一次提交。`ToolJobFinalizer` 通过 `finalizerStep` 保存已完成阶段，让可发现的中间状态能够继续执行未完成步骤。

阅读入口是 `handleTerminal()`。自动恢复路径依次执行 `ENVELOPE → RELEASE → USAGE → EVENT → CAS_STATUS → RESUME_READY`。结果摘要通过 `boundedPreview()` 限制为 16KB 的 UTF-8 安全文本，完整结果位置写入 `terminalRawRef`。`terminalAt` 由本机 `Instant.now()` 产生，更接近完成器处理时间，不能当成沙箱原始终态时间。`terminalRetryable` 必须明确存在；缺失时完成器在释放容量前停止。

`RELEASE` 从锚点恢复原容量预留，以终态信封作为释放证明。首次释放与 `ALREADY_RELEASED` 都会把 `RELEASED` 状态写回锚点。`USAGE` 与 `EVENT` 的钩子未装配或返回失败时，恢复不会继续。`CAS_STATUS` 使用一条数据库更新将 `WAITING_TOOL_JOB` 修改为 `RECEIVED` 并保存步骤。`RESUME_READY` 随后生成 `resumeToken`、增加 `resumeLeaseVersion`、写入 `READY`，然后尝试唤醒恢复服务。

`ENVELOPE`、`terminalRetryable` 回填、`RELEASE`、`USAGE`、`EVENT`、取消或失败终态、`CAS_STATUS` 和 `RESUME_READY` 的持久化调用都经过 `updateAnchor()` 或 `updateAnchorAndStatus()`。对应 SQL 只按 `id + expectedStatus` 匹配，并整块替换锚点；它没有绑定 `operationId`、`toolCallId`、`attempt`、`taskId` 或 `checkpointVersion`。数据库映射层中已有按操作身份限制的更新方法，但完成器没有调用它们。只要运行状态仍匹配，迟到的旧锚点副本就可能覆盖新字段或让 `finalizerStep` 回退。`CAS_STATUS` 只保证锚点替换与运行状态转换位于同一条更新，不提供工具作业身份栅栏。

### `run-42` 中的动作与当前扫描遗漏

`run-42` 的结果通过校验后，完成器保存 `SUCCEEDED`、结果预览、原始结果引用和实际用量；随后释放 `task-99` 对应的容量，写入用量与 `TOOL_CALL_FINISHED`，随后将运行修改为 `RECEIVED` 并生成 `READY` 恢复资格。若用户此前取消了活跃长工具，锚点中的 `autoResume=false/runDisposition=CANCELED` 会让完成器先处理终态信封、释放、用量和事件，最后将运行修改为 `CANCELED`，不会生成 `READY`。

不能把上述分步设计概括为“任意两步崩溃都必然自动恢复”。例如进程在 `EVENT` 后、`CAS_STATUS` 前崩溃时，运行仍为 `WAITING_TOOL_JOB`，活跃锚点扫描能够找到它；同一状态下若另一个完成器持有旧副本，宽更新仍可能覆盖新内容。若 `CAS_STATUS` 已成功、`RESUME_READY` 尚未写入，则数据库是 `RECEIVED + finalizerStep=CAS_STATUS + resumeState` 仍非 `READY/LAUNCHING`；该记录不满足现有两条扫描。另一个遗漏是恢复管线已经把运行写成 `COMPLETED/PARTIAL/FAILED`，但旧锚点仍为 `LAUNCHING`。Redis 辅助索引同时丢失时，这两个状态不会由当前数据库补扫发现。

`handleNotFound()` 处理“已确认终态但结果体缺失”。`terminalConfirmedAt` 只在这条路径首次发现缺失结果时设置，作为保留期限起点；它并非所有终态都有的时间字段。达到次数或时间上限后，完成器冻结 `RESULT_LOST`，再复用正常步骤释放容量并记录失败终态。

## `ToolJobEventHookImpl.java`

完整路径：`agentLangchainService/src/main/java/world/willfrog/agentlangchain/tooljob/ToolJobEventHookImpl.java`

### 为什么存在与怎样阅读

终态完成器可能在事件写入成功、确认响应返回前崩溃。重入时若再次追加普通事件，前端和审计记录会出现重复终态。该实现从数据库重新读取 `userId`，构造 `TOOL_CALL_FINISHED` 载荷，并通过 `AgentEventService.appendOnce()` 取得数据库去重所有权。

阅读 `emitTerminalEvent()` 时要同时看真实去重键和载荷。去重键是 `runId + ":" + toolCallId + ":logical_terminal"`。载荷虽然包含 `attempt`、`operation_id` 和 `task_id`，去重键却不含 `attempt` 或 `operationId`。因此代码只能保证同一个真实去重键的幂等；同一 `toolCallId` 的不同尝试次数会发生去重碰撞。教程和面试回答不能把它说成 `(runId, toolCallId, attempt)` 唯一。

### `run-42` 中的动作与失败处理

对 `run-42/call-7/attempt=1`，实际去重键为 `run-42:call-7:logical_terminal`。`appendOnce()` 首次取得该键时写入事件；再次看到相同键时视为幂等成功。事件服务抛出异常时，钩子返回 `false`，完成器停在 `EVENT`，不推进运行状态。

进程重启后，数据库去重记录使重复调用不会再次发布同一逻辑事件。不过尝试次数未进入去重键是当前实现限制；修复方向需要先明确产品按“工具调用”还是按“工具调用的每次尝试”展示终态，再调整去重身份与历史兼容策略。

## `ToolJobUsageHookImpl.java`

完整路径：`agentLangchainService/src/main/java/world/willfrog/agentlangchain/tooljob/ToolJobUsageHookImpl.java`

### 为什么存在与怎样阅读

智能体工作线程已经退出，终态用量不能依赖旧线程内的临时对象。该实现从数据库锚点重建 `DataAnalysisTerminalEnvelope`，再交给 `DataAnalysisTerminalRecorder` 幂等写入。这样完成器重入不会重复计费，也不会因为切换进程而丢掉容量身份。

先阅读 `upsertUsage()` 的成功条件：`INSERTED` 与 `ALREADY_PRESENT_SAME` 都算完成，其他结果或异常都返回 `false`。再阅读 `toEnvelope()`：它要求锚点存在、`terminalRetryable` 已经分类，并从 `reservationJson`、`estimateJson` 和 `terminalUsageJson` 还原预留、估算与实际用量。只有 `SUCCEEDED` 被标为成功；失败终态没有显式错误码时使用终态名。

### `run-42` 中的动作与失败处理

完成器释放容量后，为 `run-42` 重建包含 `call-7`、尝试次数 `1`、`operationId`、`task-99`、结果引用和资源用量的信封。数据库暂时不可用时，钩子返回 `false`，完成器停在 `USAGE`；下一轮用同一 `operationId` 身份重试。容量步骤已经完成并写回 `RELEASED` 时，用量延迟不会重新占用容量，但若释放步骤本身尚未取得证明，则不能把“用量失败不会泄漏”扩展为整个终态流程的无条件保证。

## `ToolJobRedisCache.java`

完整路径：`agentLangchainService/src/main/java/world/willfrog/agentlangchain/tooljob/ToolJobRedisCache.java`

### 为什么存在与怎样阅读

在线协调器需要快速取得已经到达 `nextPollAt` 的运行。逐轮扫描 PostgreSQL 会把轮询压力放到真相源，因此本类维护每个运行的 JSON 热副本和全局到期有序集合。它们只缩短发现时间，不参与数据库条件更新的所有权判断。

先阅读键布局：`agent:run:{runId}:pending_tool_job` 保存热副本，`agent:tool-job:due` 按 `nextPollAt` 的毫秒时间戳排序。`fetchDue(limit)` 取分值不晚于当前时间的成员。`atomicWritePendingAndDue()` 通过 Lua 在 Redis 内执行 `SET + ZADD`，让两个 Redis 结构同成同败，但它不能把 PostgreSQL 写入纳入同一个原子操作。

### `run-42` 中的动作与失败处理

`run-42` 的下一轮查询时间到来前，协调器把锚点写入热副本，并把运行标识按时间加入有序集合。到期后 `fetchDue(20)` 返回它，真正处理前仍要重新读取 PostgreSQL 锚点。TTL 覆盖任务超时和终态保留时间，最低为 60 秒。

`atomicWritePendingAndDue()` 在 JSON 序列化失败时返回 `false`；调用 `redisTemplate.execute()` 后没有检查 Lua 返回值，执行未抛异常就返回 `true`。上层多处也没有检查该布尔值。Redis 丢失不会删除数据库锚点，但如果当前数据库扫描又遗漏对应状态，不能依靠“Redis 可重建”推导出一定可恢复。数据库先成功、Redis 后更新也不是所有在线分支的统一保证：`handleNotFound()` 与协调器的非终态分支忽略 `updateAnchor()` 返回值，仍会更新 Redis；下一轮处理虽然会重新读取 PostgreSQL，Redis 在此期间可能反映未落库的内存锚点。

## `ToolJobReconciler.java`

完整路径：`agentLangchainService/src/main/java/world/willfrog/agentlangchain/tooljob/ToolJobReconciler.java`

### 为什么存在与怎样阅读

旧智能体工作线程退出后，需要独立后台服务轮询沙箱、取得结果并驱动完成器。该类提供高频到期轮询和低频数据库重建。两条任务都从 Redis 查找候选或重建 Redis，但每次真正处理运行时重新读取数据库锚点。

从 `reconcileFromDue()` 进入：每轮最多处理 20 个到期运行，单项异常不阻塞其他运行。`processItem()` 先处理检查点失败标记，再加载锚点和 `taskId`。非终态只推进 `nextPollAt`；已确认终态才请求结果、校验并调用完成器；结果缺失进入有界重试。`rebuildFromAnchors()` 先扫描活跃锚点，再扫描 `RECEIVED + READY/LAUNCHING` 的恢复记录。

### `run-42` 中的动作与暂停限制

`run-42` 到期后，协调器查询 `task-99`。终态结果通过校验时调用 `handleTerminal(..., anchor.isAutoResume())`。活跃锚点的取消路径已把 `autoResume` 设为 `false`，因此 `checkPausedTerminal()` 仍会确认沙箱终态和释放容量，但不会生成自动恢复资格。

当前 `pauseRun()` 不修改锚点的 `autoResume` 或 `runDisposition`，只把数据库状态覆盖成 `WAITING`。因此不能把 `checkPausedTerminal()` 描述成已经安全覆盖暂停与取消。活跃长工具被暂停后，协调器仍可能走自动恢复判断，而完成器的锚点写入要求旧状态为 `WAITING_TOOL_JOB`，会因当前状态为 `WAITING` 失败。数据库扫描能够看到 `WAITING + anchor`，不代表完成器能够推进。

## `ToolJobStartupRecovery.java`

完整路径：`agentLangchainService/src/main/java/world/willfrog/agentlangchain/tooljob/ToolJobStartupRecovery.java`

### 为什么存在与怎样阅读

服务重启后，内存容量账本、Redis 到期索引和本地恢复声明都已经消失。启动恢复先重建容量事实，再重建工具作业索引和恢复资格。顺序不能反转：容量身份无法证明时开放新准入，会导致超额占用。

从 `onReady()` 阅读两阶段入口。`recoverCapacityLedger()` 扫描持久预留，无法解析的记录进入隔离并让准入保持 `RECOVERING`。`recoverToolJobAnchors()` 对活跃运行处理 `EXECUTING` 附着转交、`CONSUMED` 清理、`READY/LAUNCHING` 索引重建、结果拉取待处理以及完成器步骤重入。`resolvePreparingDispatch()` 会先按 `operationId` 查询沙箱，明确没有任务时才重放同一幂等创建请求。

### `run-42` 中的动作与扫描范围

若 `run-42` 在 `READY` 写入后崩溃，启动恢复会重建 Redis 结构并调用 `tryResume()`。若它仍为 `WAITING_TOOL_JOB` 且 `finalizerStep=EVENT`，活跃锚点扫描能发现并让在线协调器继续。

现有查询并不覆盖所有锚点。活跃锚点扫描只检查 `EXECUTING/WAITING_TOOL_JOB/WAITING/CANCELED`；恢复扫描只检查 `RECEIVED` 且 `resumeState` 为 `READY/LAUNCHING`。因此 `RECEIVED + CAS_STATUS 但未 READY`，以及终态运行上残留的 `LAUNCHING` 锚点，都不属于自动发现集合。启动恢复还有批次上限，教程不能把一次启动扫描表述为无条件遍历全部历史记录。

## `ToolJobResumeService.java`

完整路径：`agentLangchainService/src/main/java/world/willfrog/agentlangchain/tooljob/ToolJobResumeService.java`

### 为什么存在与怎样阅读

`READY` 表示可以竞争恢复，`LAUNCHING` 表示某一 `resumeToken/resumeLeaseVersion` 已被接受，`CONSUMED` 是兼容与清理状态。主恢复路径在工作流接受结果后保持 `LAUNCHING + resultConsumed=true`，再按令牌和版本直接清空锚点；生产代码中没有发现 `markConsumed()` 调用。该服务用数据库条件更新推进这些阶段，并在提交新工作线程前恢复数据集登记表。它保护锚点推进、交接接受和清理；旧恢复任务的执行过程没有被完整覆盖。

阅读 `tryResume()` 的三路分支。`launchFromReady()` 冻结 `READY` 的 `resumeToken/resumeLeaseVersion`，将状态修改为 `LAUNCHING` 并增加版本。它不会在 `READY→LAUNCHING` 时生成新令牌。数据集恢复或调度提交失败时，`rollbackToReady()` 再增加版本，避免 ABA。`reenterLaunching()` 只有在持久租约 TTL 超时且本进程启动器未报告活跃时，才将旧 `LAUNCHING` 回滚为带新令牌和版本的 `READY`。

`markHandoffAccepted()` 只接受相同令牌和版本的 `LAUNCHING`，把已经消费结果后的完成前缀、新待办位置、工具次数和 `resultConsumed=true` 写回。`completeHandoff()` 只清理相同租约且已消费结果的旧锚点。

### `run-42` 中的动作与过期排队任务风险

假设完成器生成 `READY(令牌 token-A, 版本 5)`。领取成功后变成 `LAUNCHING(令牌 token-A, 版本 6)`；令牌仍为 `token-A`。恢复上下文与本地 `ClaimKey` 都使用 `token-A/6`。若数据集恢复失败，回滚为 `READY(令牌 token-A, 版本 7)`；只有过期 `LAUNCHING` 回滚路径会生成另一令牌。

本地启动器的活跃状态无法跨进程观察。旧进程的 `Runnable` 可能仍在本地队列，新进程在 TTL 后生成新租约。旧 `Runnable` 开始运行时，管线只重新读取 `AgentRun`，没有把恢复上下文中的令牌和版本与最新锚点再次比较。旧任务后续的交接与清理会被数据库条件更新拒绝，但此前发生的模型或工具副作用不会撤销。因此“只有一个工作线程真正执行恢复”超出了当前代码保证。

`completeHandoff()` 的身份检查为未来新检查点提供防误清理门槛，但当前基线不能完成同一线性运行的第二次长任务挂起：恢复期运行通常仍为 `RECEIVED`，旧锚点仍为 `LAUNCHING`，而新的 `persistPreparing()` 要求 `EXECUTING + 空锚点`。这项防御性判断不能当成已支持重复挂起的证据。

## `ToolJobResumeLauncher.java`

### 为什么存在与怎样阅读

恢复服务不应直接依赖具体运行管线，因此接口把“提交恢复任务”和“查询本地声明”抽成两个方法。`launch(runId, context)` 返回任务是否被实现接收；接受不等于已经取得线程，任务可能仍在调度器队列中。`isActive(runId, token, version)` 的默认实现返回 `false`，生产实现需要声明自己能观察的范围。

## `ToolJobResumeLauncherImpl.java`

完整路径：`agentLangchainService/src/main/java/world/willfrog/agentlangchain/tooljob/ToolJobResumeLauncherImpl.java`

### 为什么存在与怎样阅读

生产实现把恢复任务交给与普通运行共用的并发调度器，并通过本地 `ConcurrentHashMap` 避免同一 JVM 重复提交相同租约。它还连接两阶段回调：工作流接受结果后调用 `markHandoffAccepted()`，管线持久化结果后调用 `completeHandoff()`。

先阅读 `valid()`：`runId`、恢复上下文中的 `runId`、令牌、正版本和 `todoId` 都必须存在。`ClaimKey` 由 `(runId, token, version)` 构成，`putIfAbsent` 成功后重新读取 `AgentRun`，再调用 `pipeline.launchResumedAsync()`。本地声明从接受提交开始存在，覆盖排队和执行时间；它不只表示“线程正在运行”。任务拒绝、异常或持久化回调结束后会移除声明。

### `run-42` 中的动作与跨进程限制

`run-42/token-A/6` 在本 JVM 首次提交时写入 `activeClaims`。重复扫描同一三元组会返回 `true` 而不重复入队。另一进程拥有自己的本地映射，看不到这个声明。`isActive()` 因此只能回答“本 JVM 已接收且尚未结束”，不能证明另一进程没有旧任务。

若运行已被删除，提交前重新读取返回空并撤销本地声明。若调度器不接受任务，启动器返回 `false`，恢复服务回滚租约。任务已经接受但进程崩溃时，本地映射消失，数据库 `LAUNCHING` 仍保留，后续由 TTL 重入；前述旧跨进程排队任务风险仍需要管线开始运行前的租约再验证才能消除。

## `ToolJobResumeContext.java`

完整路径：`agentLangchainService/src/main/java/world/willfrog/agentlangchain/tooljob/ToolJobResumeContext.java`

### 为什么存在与怎样阅读

恢复任务需要一次传递挂起位置、已完成前缀、数据集快照、工具预算、终态结果和租约身份。该数据传输对象（DTO）把这些信息从数据库锚点带到启动器、管线和线性工作流执行器，避免恢复逻辑重新依赖旧线程内存。

按四组字段阅读：`runId/todoId/todoSequence` 定位注入点；`resumeToken/resumeLeaseVersion` 绑定本轮交接；`completedTodos/datasetSnapshotJson/datasetSnapshotDigest/toolCallsUsed` 恢复前缀与预算；`terminalSuccess/terminalResultPreview/terminalRawRef/resultConsumed` 表示终态消费进度。每次启动都创建新对象，不在多个工作线程之间共享可变实例。

### `run-42` 中的动作与失败处理

`buildResumeContext()` 为 `run-42` 写入 `todo-2`、已经完成的 `todo-1`、令牌 `token-A`、版本 6、数据集快照、累计工具次数和 `task-99` 的终态结果。工作流接受结果后会把恢复上下文的待办位置推进到下一节点，并设置 `resultConsumed=true`，再由交接回调持久化。

进程崩溃后，新对象从最新锚点重建。该数据传输对象自身不验证数据库当前租约，也不提供持久化保证；保证来自恢复服务的条件更新。检查点写入端会重新计算并比较数据集快照摘要；恢复端的 `restoreDatasetRegistry()` 直接恢复快照，不读取或比较锚点中的 `datasetSnapshotDigest`。登记表的 `restore()` 会检查编号、原始标识、产物类型、产物清单引用和内存兼容性，摘要只参与日志计算。`ToolJobResumeContext.datasetSnapshotDigest` 虽然会被赋值，主管线没有读取它，因此不能据此宣称恢复时已验证摘要或本地文件字节。

## 面试表达与配套阅读

面试官问“为什么终态后不直接将运行修改为完成状态”时，可以先说明外部结果还要经过身份校验、容量释放、用量与事件记录，随后生成恢复资格。每个步骤保存进度，使当前扫描能够发现的中间状态可以重入。随后主动说出限制：事件去重键不含尝试次数，`READY` 领取不会更换令牌，旧跨进程排队任务开始运行前缺少租约再验证，数据库扫描还遗漏两个状态窗口。

配套资料可阅读 PostgreSQL 事务隔离文档 <https://www.postgresql.org/docs/current/transaction-iso.html>、Redis 有序集合文档 <https://redis.io/docs/latest/develop/data-types/sorted-sets/> 和 Temporal Durable Execution 资料 <https://assets.temporal.io/durable-execution.pdf>。这些资料用于理解条件更新、到期索引与持久执行原则；AlphaFrog 的实际保证仍以本章列出的项目代码为准。
