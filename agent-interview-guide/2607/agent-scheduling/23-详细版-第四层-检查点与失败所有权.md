# 详细版第四层：检查点与失败所有权

源码基线：`2e463aa290a17c01eec45d229162db3952a42e6f`

完整计划在执行待办前已由 `persistPlan()` 写入 `AgentRun.plan_json` 与 Redis，恢复端会从 `run.getPlanJson()` 读取，检查点请求没有计划字段。第三层又让 `run-42` 进入 `WAITING_TOOL_JOB`，把 `task-99` 的身份和容量责任写入 PostgreSQL；其 `PREPARING` 锚点已经保存挂起位置 `todo-2`、顺序、资源估算、数据集快照与摘要。

此时仍只存在于旧工作线程的恢复事实是 `todo-1` 的完成前缀、数据引用和实际工具调用次数。第四层不会保存计划；它把这三项冻结并补入检查点，同时使用 `checkpointVersion` 对待办位置、数据集快照和资源估算做窄合并与复核。若写入失败，它还要回答：谁负责标记失败、谁负责稍后重试、当前失败是否已经被另一份更高版本的健康检查点取代。

推荐阅读顺序是 `ToolJobCheckpointWriter` → `ToolJobCheckpointRequest` → `ToolJobCheckpointService` → `ToolJobAnchorService` → `ToolJobCheckpointFailureRecoveryService`。

## 1. `ToolJobCheckpointWriter.java`：定义“成功保存后才能结束工作线程”

文件路径：

`agentLangchainService/src/main/java/world/willfrog/agentlangchain/tooljob/ToolJobCheckpointWriter.java`

### 1.1 为什么存在

执行管线负责判断工作流是否暂停，却不应了解数据库 JSON 合并、字段类型校验和数据库映射层细节。`ToolJobCheckpointWriter` 用一个函数式接口表达管线真正需要的承诺：把完整 `ToolJobCheckpointRequest` 原子保存，只有条件更新成功才返回 `true`。

这个返回值具有业务含义。它表示数据库已经接受当前身份、版本和恢复上下文。普通的“调用没有抛异常”不足以证明旧工作线程可以结束。

### 1.2 从哪里开始阅读

接口只有一个方法：

`boolean captureAndSave(ToolJobCheckpointRequest request)`（23 行）

先阅读方法注释，再查看调用者 `LangchainLinearRunPipelineImpl.persistToolJobCheckpoint()`。执行管线收到挂起结果后，从最新锚点取得任务身份和 `checkpointVersion`，捕获数据集快照与已完成待办，然后调用这个接口。

生产实现是 `ToolJobCheckpointService`。接口放在独立文件中，也便于单元测试向管线注入明确的成功或失败行为。

### 1.3 `run-42` 在这里发生什么

`todo-2` 抛出的挂起控制信号已经到达执行管线。管线构造请求后调用 `captureAndSave()`。返回 `true` 表示本次调用已经保存检查点，管线可以发布 `TOOL_CALL_SUSPENDED` 并结束当前 `Runnable`。

若返回 `false`，管线先调用 `recordCheckpointFailure()`，把冻结请求交给 `ToolJobCheckpointFailureRecoveryService`。只有 `HEALTHY_CHECKPOINT` 证明另一位写者已经保存等价新版本时，管线才继续发布挂起事件。其余处理结果都会结束本次执行片段：`FAILURE_OWNED` 已持久化失败处置，`RETRY_OWNED` 已持久化重试请求；`SUPERSEDED` 只说明冻结身份判断已经不成立，`UNOWNED` 则没有持久处理者。后两种情况仍是当前实现限制。因此本接口位于“后台任务已经存在”和“工作线程能否按健康检查点继续”之间。

### 1.4 失败或重启后的行为

实现未装配、字段捕获失败、数据库条件更新未取得资格，都会让接口返回 `false`。此时执行管线不会把检查点描述成已保存。

当前源码还有一个需要如实说明的窗口：若失败恢复返回 `UNOWNED`，管线仍会结束本次执行片段。教程不能把这个结果解释成已有持久处理者。后面的失败恢复文件会详细说明五种处理结果。

### 1.5 与后续文件的连接

接口只说明“保存什么动作”。具体载荷由 `ToolJobCheckpointRequest` 定义。下一步先理解哪些字段用于证明任务身份，哪些字段用于重建工作流。

## 2. `ToolJobCheckpointRequest.java`：冻结一次检查点写入的身份与上下文

文件路径：

`agentLangchainService/src/main/java/world/willfrog/agentlangchain/tooljob/ToolJobCheckpointRequest.java`

### 2.1 为什么存在

检查点写入横跨多个步骤：执行管线读取锚点、捕获内存现场、校验字段、执行数据库更新。若这些字段仍引用可变集合，或写入服务自行换成数据库中的新版本，延迟写者可能覆盖另一位执行者刚保存的现场。

`ToolJobCheckpointRequest` 的标量字段都使用 `final`。`completedTodos` 会包装成不可修改视图。当前实现没有防御性复制原列表，也没有深复制 `CompletedTodoRecord`，所以调用方在 `build()` 后仍需停止修改原列表和记录对象。执行管线当前使用方法内新建列表，构造请求后不会继续修改它。

### 2.2 从哪里开始阅读

先阅读字段定义（16—40 行），再阅读 `builder()` 与构造器（79—130 行）。字段可以分成两组。

第一组用于数据库条件更新：

- `runId`：定位 `run-42` 数据库记录；
- 操作标识 `operationId`、工具调用标识 `toolCallId`、尝试次数 `attempt`、任务标识 `taskId`：绑定同一外部操作、逻辑工具调用轮次和沙箱任务；
- `expectedCheckpointVersion`：表示管线捕获现场时看到的版本。

第二组用于恢复工作流：

- `todoId`、`sequence`：指向 `todo-2` 及其顺序；
- `completedTodos`：保存无需重新执行的完成前缀；
- `datasetSnapshotJson` 与 `datasetSnapshotDigest`：保存运行内数据集登记表及摘要；
- `datasetRefsJson`：保存数据引用；
- `toolCallsUsed`：延续运行级工具预算；
- `estimateJson`：供终态信封和容量释放使用。

随后阅读 `builder(runId)`（79—81 行）与构造器的 `build()`（122—130 行）。`expectedCheckpointVersion()`（106—112 行）除了保存整数，还将 `versionExplicitlySet` 修改为 `true`。`build()` 会拒绝从未显式设置版本的请求，即使 Java 默认值恰好为 0。

### 2.3 `run-42` 在这里发生什么

执行管线先使用最新锚点构造一个最小请求，保存操作标识、`call-7`、尝试次数、`task-99`、版本、`todo-2` 和工具调用计数。这样即使数据集快照依赖缺失，失败处置仍然有稳定身份可用。

依赖齐全后，管线重新构造完整请求：`completedTodos` 包含 `todo-1`，数据集快照来自 `AgentRunDatasetRegistry.snapshot(run-42)`，摘要来自 `immutableDigest()`，估算沿用锚点中的 `estimateJson`。

当前管线不会在请求交给保存服务后继续修改完成记录。数据库条件中的版本仍是捕获时版本，保存服务不会把它替换成稍后看到的新版本。

### 2.4 失败或重启后的行为

忘记调用 `expectedCheckpointVersion()` 会在构造期抛出 `IllegalStateException`，防止默认 0 意外通过旧数据条件。其余字段的完整性由保存服务在读取最新锚点后校验。

失败恢复需要跨进程重建同一请求。`ToolJobCheckpointFailureRecoveryService.PendingFailure` 会序列化这些字段，并通过 `toRequest()` 使用同一个构造器恢复冻结元组。这样重启后的重试不会凭当前内存猜测原请求。需要注意，类名表达不可变请求的设计目标；列表没有防御性复制是当前实现限制。

### 2.5 与后续文件的连接

请求只负责保存数据，不负责验证数据。`ToolJobCheckpointService` 会重新读取 `run-42`，比较身份与版本，并检查数据集快照、引用和估算是否具有正确类型。

## 3. `ToolJobCheckpointService.java`：校验完整现场并执行窄化条件更新

文件路径：

`agentLangchainService/src/main/java/world/willfrog/agentlangchain/tooljob/ToolJobCheckpointService.java`

### 3.1 为什么存在

旧工作线程准备结束时，内存里看似有一份完整现场。数据库可能已经被并发执行者推进，数据集快照也可能序列化错误。`ToolJobCheckpointService implements ToolJobCheckpointWriter` 在数据库更新前重新核对身份、版本和字段类型。

它只写入检查点负责的字段。容量预留、终态和完成器进度可能由后台线程同时更新，检查点不能使用旧锚点全量覆盖这些字段。

### 3.2 从哪里开始阅读

先完整读取 `captureAndSave()`（44—139 行）。该方法可以分为五段：

1. 校验 `runId`，使用 `agentRunMapper.findById()` 重读最新运行；
2. 从 `toolJobAnchorJson` 解析最新 `ToolJobAnchor`；
3. 调用 `validateIdentity()` 比较操作标识、工具调用标识、尝试次数与任务标识；
4. 比较请求版本与锚点的 `checkpointVersion`，再调用 `validateCheckpointFields()`；
5. 序列化已完成待办列表，调用 `anchorService.checkpointUpdate()`。

`validateIdentity()` 位于 141—187 行。`validateCheckpointFields()`（199—228 行）继续调用三个方法：

- `validateSnapshotType()`（230—260 行）：按 `AgentRunDatasetSnapshot` 反序列化，并重新计算 `immutableDigest()`；
- `validateRefsType()`（262—291 行）：要求根节点为 JSON 数组，元素都为字符串；
- `validateEstimateType()`（293—310 行）：要求可以构造 `DataAnalysisEstimate`。

`serializeTodos()` 把完成前缀保存为 JSON；合法空列表规范成 `[]`。

主要字段是 `agentRunMapper`、`anchorService` 和一个允许未知字段的专用 `ObjectMapper`。

### 3.3 `run-42` 在这里发生什么

`captureAndSave()` 重读 `run-42`。在本例的正常路径中，运行已处于 `WAITING_TOOL_JOB`，锚点已绑定 `task-99`。服务先确认请求中的操作标识、`call-7`、尝试次数和 `task-99` 与数据库一致，再确认请求版本等于锚点当前版本。

接着它验证 `todo-2`、`todo-1` 完成前缀、数据集快照、摘要、引用、工具调用次数和资源估算。验证通过后，`checkpointUpdate()` 执行一条数据库更新。需要注意，服务把刚读到的任意 `run.getStatus()` 作为 SQL 的预期状态；它只防止“读取后状态又变化”，并没有强制状态必须是 `WAITING_TOOL_JOB`。`WHERE` 还约束任务身份、任务标识与旧版本；`SET` 只合并检查点白名单，并在数据库内递增 `checkpointVersion`。

返回 `true` 表示恰好一行受到更新。此时新工作线程可以恢复相同数据集编号、跳过 `todo-1`，并延续原工具预算。

### 3.4 失败或重启后的行为

运行不存在、四元身份漂移、版本不同、待办缺失、顺序值为负、工具次数为负、快照摘要不一致、引用类型错误或估算无法解析，都会返回 `false`。`toolJobAnchorJson` 为空或损坏时，`ToolJobAnchor.fromJson()` 会抛出异常；本方法没有在内部把它转换为 `false`，外层管线会捕获该异常并把本次检查点尝试记为失败。

数据库更新返回零行也会返回 `false`。这通常表示状态、任务身份或版本在验证后又发生变化。服务不会刷新版本并再次覆盖，因为那会让延迟写者借用新版本。另一个限制是：若检查点恰好在 `WAITING` 等非 `WAITING_TOOL_JOB` 状态写入成功，后续失败处置 SQL 仍固定要求 `WAITING_TOOL_JOB`；检查点写入条件与失败持有条件并不完全相同。

进程重启后，已经返回 `true` 的检查点位于 PostgreSQL。恢复服务会读取同一锚点并恢复数据集登记表。若本方法尚未成功，只有 `RETRY_OWNED` 表示 `lastError` 中已保存完整失败标记供后台协调器重试；`FAILURE_OWNED` 只有锚点中的窄失败处置，`HEALTHY_CHECKPOINT` 不需要标记，`SUPERSEDED` 与 `UNOWNED` 都没有在本次处理里建立标记。若后台协调器以后发现已有的旧标记不再属于当前冻结身份，它才会按原字符串清除。

### 3.5 与后续文件的连接

本类把数据库动作委托给 `ToolJobAnchorService`。后续文件说明各种锚点写入怎样转换成数据库映射层条件更新，以及检查点写入为什么只合并一组字段。

## 4. `ToolJobAnchorService.java`：统一解释数据库更新是否取得资格

文件路径：

`agentLangchainService/src/main/java/world/willfrog/agentlangchain/tooljob/ToolJobAnchorService.java`

### 4.1 为什么存在

`tool_job_anchor_json` 同时被分发、检查点、终态完成和恢复租约使用。若各服务直接调用数据库映射层，很容易让调用者选错条件强度。`ToolJobAnchorService` 提供多种入口，但这些入口携带的条件并不相同：通用更新只比较运行状态，活跃分发更新再比较操作标识，检查点更新增加任务标识与版本，恢复租约更新再比较令牌与租约版本。

`ToolJobAnchorService` 是锚点的统一业务写入口。每个布尔值都表示数据库是否恰好更新一行。返回 `false` 代表当前调用没有取得对应修改资格，调用者需要重读数据库。

### 4.2 从哪里开始阅读

可以把方法分成五组。`loadAnchor()` 位于 31—40 行，检查点相关方法 `markCheckpointFailed()` 位于 99—105 行、`checkpointUpdate()` 位于 159—179 行；其余方法按源码顺序补充阅读。

第一组是读取与通用更新：

- `loadAnchor()` 每次从 PostgreSQL 读取并解析；损坏 JSON 会抛出异常；
- `updateAnchor()` 要求运行状态匹配；
- `updateAnchorAndStatus()` 在同一次数据库更新中保存锚点与运行状态。

第二组服务沙箱分发：

- `claimPreparing()` 只在旧锚点为空时建立 `PREPARING`；
- `updateActive()` 按操作标识更新活跃锚点；
- `updateActiveAndStatus()` 同时约束操作标识、旧运行状态并写入新状态；
- `clearActive()` 只有操作标识仍匹配时才清理。

第三组服务检查点与失败处置：

- `checkpointUpdate()` 调用 `updateToolJobCheckpoint`，一次传入待办、完成前缀、快照、引用、工具次数与估算；
- `markCheckpointFailed()` 只合并处置方式、自动恢复开关与错误，不覆盖容量预留或终态字段。

第四组服务后台扫描与状态推进：

- `casUpdateStatus()` 只在预期状态匹配时推进运行；
- `listActive()` 与 `listResumeReady()` 为 PostgreSQL 补扫提供有限批量记录。

第五组服务恢复租约：

- `casResumeState()` 同时比较状态、令牌与租约版本；
- `clearAnchorWithToken()` 只清理完全匹配的恢复声明。

### 4.3 `run-42` 在这里发生什么

第三层已经通过 `claimPreparing()`、`updateActive()` 和 `updateActiveAndStatus()` 保存了 `task-99`。进入第四层后，`checkpointUpdate()` 使用同一操作标识、`call-7`、尝试次数、`task-99` 与旧版本，合并 `todo-2` 的恢复现场。

如果保存服务失败，`markCheckpointFailed()` 会尝试在相同冻结元组上写入 `CHECKPOINT_FAILED` 处置。SQL 只修改失败相关字段，避免旧管线破坏后台已经写入的容量预留、终态或完成进度。

PostgreSQL 18 文档说明，并发 `UPDATE` 在等待另一事务提交后会对新行版本重新检查 `WHERE` 条件；受影响行数为 0 表示没有行受到修改。AlphaFrog 按动作选择条件：通用更新使用预期状态，分发更新增加操作标识，检查点更新增加工具调用标识、尝试次数、任务标识与版本，恢复租约更新使用恢复状态、令牌与租约版本。Java 再通过 `rows == 1` 判断本次动作是否取得资格。

### 4.4 失败或重启后的行为

所有更新都把 `rows == 1` 作为成功。零行不等同于数据库故障，它也可能表示另一位执行者已推进状态或版本。调用者需要重读并分类。

Redis 丢失不会改变本类读取的事实。`listActive()` 与 `listResumeReady()` 支持后台从 PostgreSQL 补建发现索引，但它们只扫描源码列出的有限状态组合：前者扫描 `EXECUTING`、`WAITING_TOOL_JOB`、`WAITING`、`CANCELED`，后者扫描 `RECEIVED` 且恢复状态为 `READY` 或 `LAUNCHING` 的记录。它们不构成覆盖任意状态的保证。解析损坏锚点会显式失败，避免把“无法解析”误判成“没有任务”。

`clearAnchorWithToken()` 没有按运行标识强制清空的旁路。即使旧恢复线程稍后完成，只要令牌或版本已变化，它也不能删除新恢复记录。

### 4.5 与后续文件的连接

`checkpointUpdate()` 返回 `false` 后，仍需区分三种情况：另一位写者已经保存了等价新版本；当前写者成功取得失败处置权；当前写者没有持久处理者。`ToolJobCheckpointFailureRecoveryService` 专门完成这项分类。

## 5. `ToolJobCheckpointFailureRecoveryService.java`：为检查点失败寻找持久处理者

文件路径：

`agentLangchainService/src/main/java/world/willfrog/agentlangchain/tooljob/ToolJobCheckpointFailureRecoveryService.java`

### 5.1 为什么存在

沙箱任务已转入后台后，检查点可能因为版本竞争、数据库瞬时异常或字段问题而失败。当前工作线程即将结束，单纯记录日志无法保证有人继续处理。另一方面，不能看到一次失败就将运行标记为失败，因为另一位并发写者可能已经保存了等价或更高版本检查点。

本服务使用冻结任务元组判断失败属于谁，并在必要时把完整请求编码进 `AgentRun.lastError` 失败标记。后台协调器会优先处理这个标记，成功前不会继续正常沙箱轮询与恢复。

### 5.2 从哪里开始阅读

先阅读 `handleFailure()`（41—84 行），再阅读 `retryPending()`（87—119 行）。持有者判断位于 `hasSameFrozenOwner()`（127—149 行）和 `hasEquivalentOrNewerCheckpoint()`（167—197 行），持久失败标记的数据记录 `PendingFailure` 位于 217—235 行。

`handleFailure()` 的判断顺序如下：

1. 请求为空时返回 `UNOWNED`；
2. `hasEquivalentOrNewerCheckpoint()` 已证明健康新版本时返回 `HEALTHY_CHECKPOINT`；
3. 调用 `anchorService.markCheckpointFailed()`，成功时返回 `FAILURE_OWNED`；
4. 再次检查健康新版本，处理并发写入窗口；
5. 生成“标记前缀 + `PendingFailure` JSON”，数据库保存成功时返回 `RETRY_OWNED`；
6. 冻结持有者已变化时返回 `SUPERSEDED`；
7. 同一失败标记已存在时幂等返回 `RETRY_OWNED`；
8. 对同一持有者做一次有限的窄写重试；
9. 最终根据持有者是否仍相同返回 `UNOWNED` 或 `SUPERSEDED`。

`retryPending()` 从数据库读取失败标记，通过 `PendingFailure.toRequest()` 重建原请求。它先检查健康新版本，再检查持有者是否已经变化；同一持有者仍有效时再次执行窄失败合并。处理完成后使用原标记做精确比较后清除，避免删除另一条新错误。

主要字段是 `anchorService`、`runMapper`、`objectMapper` 和常量 `MARKER_PREFIX`。

### 5.3 `run-42` 在这里发生什么

假设 `run-42` 的检查点版本为 3，管线保存 `todo-2` 现场时返回 `false`。`handleFailure()` 使用操作标识、`call-7`、尝试次数、`task-99` 与预期版本 3 查询数据库。

若数据库已经出现版本 4，并且待办、完成前缀、数据快照、引用、工具次数和估算与请求结构等价，结果是 `HEALTHY_CHECKPOINT`。当前写者退出，`run-42` 继续保持可恢复。

若版本仍为 3，本服务尝试将同一任务的处置方式修改为 `CHECKPOINT_FAILED`，关闭自动恢复并记录错误。成功后返回 `FAILURE_OWNED`。

若窄写暂时失败，本服务把完整请求写入 `lastError` 失败标记，返回 `RETRY_OWNED`。`ToolJobReconciler.processItem()` 每轮先调用 `retryPending(run-42)`；标记未解决时直接返回，不会继续查询 `task-99` 并启动一个缺少工作流现场的恢复执行。

### 5.4 五种处理结果怎样理解

- `HEALTHY_CHECKPOINT`：另一位写者已保存结构等价且版本更高的检查点；本次失败不需要终止运行。
- `FAILURE_OWNED`：当前调用已把检查点失败处置写入数据库。
- `RETRY_OWNED`：数据库已保存可跨进程恢复的失败标记，后台协调器负责稍后重试。
- `SUPERSEDED`：`hasSameFrozenOwner()` 返回 `false`。它要求运行存在、状态正好为 `WAITING_TOOL_JOB`、锚点非空，并且操作标识、工具调用标识、尝试次数、任务标识与版本全部相同。任一条件不成立都进入该结果；例如同一身份和版本的运行若已变为 `WAITING`，也会被判为 `SUPERSEDED`，旧标记可被按原字符串清除。因此这个结果不能单独证明已有新持有者。
- `UNOWNED`：仍无法证明有健康检查点，也没有成功建立失败或重试处理者。

`UNOWNED` 是当前实现需要明确保留的限制。执行管线在收到该结果后仍会结束当前执行片段。它只能说明本次补偿没有取得持久处理权，不能描述成故障已经得到可靠处理。

### 5.5 失败或重启后的行为

`hasSameFrozenOwner()` 每次从 PostgreSQL 重读运行，要求状态为 `WAITING_TOOL_JOB`、锚点存在，并逐项比较操作标识、工具调用标识、尝试次数、任务标识与版本。分类过程异常时保守返回 `true`，避免错误清除仍有效的失败处理者。

`hasEquivalentOrNewerCheckpoint()` 还会结构化比较已完成待办、数据快照、引用和估算 JSON。字段顺序变化不影响比较，内容差异会阻止把它判成健康等价版本。

进程重启后，失败标记仍位于 `lastError`。后台协调器重建到期任务后先调用 `retryPending()`。失败处置已保存、健康版本已存在，或冻结持有条件已不成立时，原标记才会按原字符串清除。最后一种情况也可能只是运行状态离开了 `WAITING_TOOL_JOB`，并不必然表示出现了新持有者。

非法失败标记无法反序列化时返回 `false`，后台停止推进该运行，等待人工或后续修复。这个选择可以避免在缺少检查点时继续恢复模型执行。

### 5.6 与下一层的连接

检查点成功后，旧工作线程可以归还；沙箱终态由后台协调器获取。检查点失败标记也由后台协调器优先处理。下一层会继续阅读 `ToolJobReconciler`、结果校验、容量释放、用量事件与恢复租约。

## 6. `run-42` 的完整检查点时序

```text
PENDING + WAITING_TOOL_JOB 已经写入数据库
  → 挂起控制信号到达执行管线
  → 管线重读最新锚点与 checkpointVersion
  → 构造最小 ToolJobCheckpointRequest
  → 捕获已完成待办、数据集快照、数据引用、工具调用次数和估算
  → 构造字段完整的冻结请求；调用方此后不再修改原列表
  → ToolJobCheckpointService 校验身份、版本和字段类型
  → ToolJobAnchorService.checkpointUpdate 执行窄化条件更新
  → 成功：发布 TOOL_CALL_SUSPENDED，旧工作线程结束
  → 失败：ToolJobCheckpointFailureRecoveryService 分类
       ├─ HEALTHY_CHECKPOINT：采用并发写者的健康新版本
       ├─ FAILURE_OWNED：数据库保存失败处置
       ├─ RETRY_OWNED：lastError 保存完整失败标记
       ├─ SUPERSEDED：冻结持有条件已不成立，旧写者退出
       └─ UNOWNED：当前实现仍存在的未持有窗口
```

阅读时可以用四个问题检查理解：

1. 为什么请求必须冻结旧版本？延迟写者不能借用更新版本覆盖更近现场。
2. 为什么写入检查点时要验证数据集摘要？保存服务会重新计算快照摘要，拒绝正文与摘要不一致；但恢复入口只解析快照并调用登记表的 `restore()`，不会再次把锚点中的 `datasetSnapshotDigest` 与正文重算值比较，这是当前限制。
3. 为什么检查点只合并白名单字段？后台线程可能同时写入容量预留、终态和完成器进度。
4. 为什么失败恢复先检查健康新版本？一次本地失败不能自动证明整次运行缺少可恢复检查点。
