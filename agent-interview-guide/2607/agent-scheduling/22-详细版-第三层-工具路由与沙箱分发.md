# 详细版第三层：工具路由与沙箱分发

源码基线：`2e463aa290a17c01eec45d229162db3952a42e6f`

这一层解决的问题是：模型已经决定调用 `executePython`，Java 服务怎样把一次 LangChain4j 工具请求转换成可追踪、可限流、可恢复的沙箱任务。

贯穿示例继续使用 `run-42`。`todo-2` 需要 Python 计算最大回撤，模型生成工具调用 `call-7`，沙箱返回任务编号 `task-99`。短任务可以在当前工作线程内返回。长任务要先把操作身份、容量责任和沙箱任务写入 PostgreSQL，再让当前工作线程结束。

推荐阅读顺序是 `ToolRouterToolExecutor` → `ToolRouter` → `PythonSandboxTools` → `PythonSandboxDispatchStoreImpl`。这个顺序贴近一次真实调用从 LangChain4j 进入业务工具、再进入持久分发的方向。

## 1. `ToolRouterToolExecutor.java`：把 LangChain4j 工具请求交给平台路由器

文件路径：

`agentLangchainService/src/main/java/world/willfrog/agentlangchain/tools/ToolRouterToolExecutor.java`

### 1.1 为什么存在

LangChain4j 只知道模型发起了哪个工具、参数 JSON 是什么。AlphaFrog 还需要稳定的工具调用编号、运行上下文、重复调用防护、工具并发限制、运行事件和数据集引用。把这些动作散落到每个业务工具会产生重复实现，也容易让不同工具的事件顺序不一致。

`ToolRouterToolExecutor implements ToolExecutor` 提供这一层适配。LangChain4j 官方文档说明，每个动态 `ToolSpecification` 都要配一个 `ToolExecutor`，该执行器负责处理模型生成的工具请求。AlphaFrog 在这个扩展点内完成平台动作，再把业务执行交给 `ToolRouter`。

### 1.2 从哪里开始阅读

先阅读 `executeWithContext()`（173—180 行），再进入 `execute()`（101—166 行）。

`executeWithContext()` 从 `InvocationContext.invocationParameters()` 恢复 `AgentContext`，随后调用 `execute()`。这里实际经 `LangchainRunContextBridge.apply()` 写入的只有 `runId`、`userId` 和 `webSearchEnabled`。工作流执行器在更早阶段写入阶段与步骤，`LangchainTodoNodeExecutor` 在进入节点时写入 `todoId` 与 `todoSequence`；本文件只是在工具入口复用这些既有值。

`execute()` 是主要入口。阅读时按以下顺序定位：

1. `resolveToolCallId()`：优先采用 LangChain4j 请求中的编号；缺失时生成 UUID。
2. `parseArguments()`：把参数 JSON 解析为 `Map<String, Object>`。
3. `LangchainRepeatedToolCallGuard.beforeInvoke()`：检查同一工具与同一参数是否反复出现。
4. `emitToolCallStarted()`：发布 `TOOL_CALL_STARTED`。
5. `toolThrottle.tryAcquire()`：取得工具级并发许可。
6. `toolRouter.invokeWithMeta()`：进入平台路由器。
7. `emitToolCallFinished()`：只对已经得到逻辑终态的调用发布完成事件。
8. `acknowledgeSynchronousPythonCompletion()`：同步 Python 调用结束后清理活跃分发。
9. `DatasetRefRegistry.registerFromJson()`：从结果登记数据集引用。

主要字段包括 `toolRouter`、`objectMapper`、`eventService`、`toolThrottle` 和 `pythonSandboxDispatchStore`。`OUTPUT_PREVIEW_MAX_CHARS = 500` 只限制事件预览，不会截断返回给模型的工具正文。

### 1.3 `run-42` 在这里发生什么

模型提交 `executePython`，请求编号为 `call-7`。`executeWithContext()` 把调用参数中的 `runId=run-42`、用户编号和联网开关写入 `AgentContext`；`todo-2` 的位置已经由 `LangchainTodoNodeExecutor` 预先写入。`execute()` 再把 `call-7` 放入 `AgentContext.toolCallId`，因此后面的 `PythonSandboxTools` 可以使用 `run-42 + call-7 + attempt` 构造稳定操作编号。

参数解析和重复检查通过后，本类发布 `TOOL_CALL_STARTED`。事件内包含 `tool_call_id=call-7`、工具名、参数以及待办归属。随后取得工具并发许可并调用 `ToolRouter.invokeWithMeta("executePython", params)`。

如果沙箱在短轮询窗口内完成，调用返回普通结果。本类记录耗时，发布带固定去重标识的 `TOOL_CALL_FINISHED`，然后调用 `acknowledgeSynchronousPythonCompletion()`。该方法用 `run-42`、`call-7` 和 `attempt=1` 重新计算操作标识 `operationId`，仅清理仍属于这次同步调用的活跃锚点。

如果沙箱仍在运行，`PythonSandboxTools` 会抛出 `ExternalToolJobPendingException`。`execute()` 在第 136 至 141 行原样抛出，不发布 `TOOL_CALL_FINISHED`。此时工具只有“已开始”和“后台运行中”的事实，逻辑终态要等后台完成器发布。

### 1.4 失败或重启后的行为

参数 JSON 无法解析时，`parseArguments()` 保存 `raw` 字段，避免空指针中断工具循环。重复调用被阻止时，本类直接发布失败的完成事件，使前端工具卡片停止等待。工具并发许可获取失败会作为文本返回给模型，运行不会因此自动进入恢复流程。

普通工具异常也会转换成失败输出。`ExternalToolJobPendingException` 受到单独处理，因为它携带的是控制信息。若将它转换为字符串，模型会误以为 Python 已经结束，并可能继续生成 `todo-2` 的结论。

进程在发出挂起信号后退出，也不会依赖本类的内存字段。此时数据库已经保存沙箱任务与运行状态，后台扫描可以继续。同步完成后的 `clearActive()` 也带操作标识条件，旧调用无法清除一轮新的沙箱任务。

### 1.5 与后续文件的连接

本类处理 LangChain4j 侧的上下文、事件和工具并发。实际预算检查、缓存调用、参数别名和工具名分派位于 `ToolRouter`。因此下一步应沿 `toolRouter.invokeWithMeta()` 继续阅读。

## 2. `ToolRouter.java`：统一预算、限流、缓存与工具名分派

文件路径：

`agentToolsShared/src/main/java/world/willfrog/agent/tools/router/ToolRouter.java`

### 2.1 为什么存在

平台同时暴露行情、检索、文档、Python 和数据登记等工具。不同上层执行器都需要一致的预算检查、压测故障注入、按有效资源权重限流、结果缓存策略、观测记录和错误格式。`ToolRouter` 把这些通用动作放在一次工具调用的固定入口中。

它还承担参数兼容。模型可能输出 `dataset_ids`、`datasetIds` 或旧位置参数；具体工具实现只应接收一种规范形态。

### 2.2 从哪里开始阅读

先阅读 `invokeWithMeta()`（189—291 行），再定位 `executeDirect()`（469—675 行），最后进入 `invokeExecutePython()`（384—409 行）。数据集与清单的参数兼容分别位于 `collectExecutePythonDatasetIds()`（703—717 行）和 `collectExecutePythonManifestIds()`（739—750 行）。

`invoke()` 只是兼容入口，返回 `invokeWithMeta()` 的输出字符串。`invokeWithMeta()` 的主要步骤如下：

1. 使用 `budgetService.checkBeforeToolCall()` 检查运行工具预算；`checkParallelLimits` 例外。
2. 应用压测延迟或失败注入。
3. 使用 `toolWeightedLimitService.tryAcquire()` 按工具实际资源权重取得许可。
4. 调用 `toolResultCacheService.executeWithCache()`；是否复用缓存由缓存服务决定。
5. 缓存需要实际执行时调用 `executeDirect()`。
6. 记录观测、耗时与缓存元数据。
7. 在 `finally` 释放权重许可。

`supportedTools()` 返回平台理论支持的工具名。某些能力仍会在 `executeDirect()` 进行运行级开关检查。

`executeDirect()` 使用 `switch` 选择具体工具。`case "executePython"` 调用 `invokeExecutePython()`。后者先通过 `collectExecutePythonDatasetIds()` 和 `collectExecutePythonManifestIds()` 分别规范两个编号空间，再执行 `PythonStaticPrecheckService.check()`，最后调用五参数 `PythonSandboxTools.executePython()`。

### 2.3 `run-42` 在这里发生什么

`call-7` 已经在前述文件写入 `AgentContext`。`invokeWithMeta()` 检查 `run-42` 是否还有工具调用预算，并为 `executePython` 取得工具权重许可。

假设模型传入：

```json
{
  "code": "...",
  "dataset_ids": [1, 2],
  "libraries": "pandas",
  "timeout_seconds": 30
}
```

`invokeExecutePython()` 把数据集编号整理成 `1,2`。清单编号使用独立集合，旧位置参数 `arg1` 只进入数据集编号空间，避免一个数字同时代表两类对象。静态检查通过后，代码、编号、依赖和超时进入 `PythonSandboxTools`。

### 2.4 失败或重启后的行为

预算耗尽会在业务工具运行前抛出预算控制异常。权重许可不足会返回结构化失败，模型可以稍后缩小任务。静态检查失败会返回 `pre_validation_failed` 信息，沙箱不会收到请求。

`executeDirect()` 对普通异常调用 `invocationError()`。它对 `ExternalToolJobPendingException` 采用单独的 `catch` 并重新抛出。挂起时还没有终态结果，因此本类不会写入普通工具结果缓存，也不会清理沙箱容量预留。`invokeWithMeta()` 的 `finally` 只释放工具权重许可；沙箱容量由持久任务继续持有。

进程重启后，不会从 `ToolRouter` 的内存状态恢复。恢复所需身份已经由后续文件写入持久化锚点。本类重新被调用时仍会按预算、限流和参数规则处理新的逻辑调用。

### 2.5 与后续文件的连接

`ToolRouter` 把模型参数规范成沙箱工具需要的输入。数据集编号解析、容量估算、幂等创建、短轮询和转后台都位于 `PythonSandboxTools`。下一步从五参数 `executePython()` 进入。

## 3. `PythonSandboxTools.java`：创建可追踪的 Python 任务并决定同步返回或转后台

文件路径：

`agentToolsShared/src/main/java/world/willfrog/agent/tools/python/PythonSandboxTools.java`

### 3.1 为什么存在

Python 沙箱位于独立服务。Java 侧需要把运行内的短数据编号解析成可挂载数据，构造沙箱请求，并处理创建 RPC 的不确定结果。长任务还要管理资源估算、容量预留、稳定操作编号、请求指纹、数据库锚点和短轮询窗口。

这些动作必须集中在创建任务的一侧。否则上层只能看到“调用超时”，无法判断沙箱是否已经创建任务，也无法在进程重启后找到它。

### 3.2 从哪里开始阅读

先阅读五参数 `executePython()`（139—141 行），它直接调用 `executePythonInternal()`（165—410 行）。四参数重载位于 148—150 行，只为旧调用方保留。

`executePythonInternal()` 前半段处理输入数据：

- `parseDatasetIds()` 解析数据集与清单的运行内编号；
- `AgentRunDatasetRegistry` 把短编号解析为持久数据条目；
- 清单会补充其成员数据集；
- `AgentRunDatasetCsvWriter` 生成沙箱内的数据路径 CSV；
- `ExecuteRequest` 保存代码、数据、依赖和超时。

随后查看 `dataIntenseWiringAvailable()`（412—417 行）。容量服务、分发存储、配置和终态记录器都已装配时，代码进入 `executeDataIntense()`（419—663 行）。快速终态位于 `completeSynchronously()`（665—735 行），转后台位于 `suspend()`（737—770 行）。

`executeDataIntense()` 的顺序如下：

1. 从 `AgentContext` 取得 `toolCallId`，以 `attempt=1` 构造 `DataAnalysisOperationIdentity`。
2. 汇总数据行数和字节数，选择资源档位与容量单位。
3. 调用 `dataAnalysisCapacityService.reserve()`，取得状态为 `PREPARING` 的容量预留。
4. 构造 `CanonicalSandboxCreateSpec` 与 `requestFingerprint`。
5. 在 `createTask` 前调用 `pythonSandboxDispatchStore.persistPreparing()`。
6. 调用沙箱 `createTask()`；RPC 结果不确定时按操作标识 `operationId` 查询。
7. 得到任务标识 `taskId` 后，把容量预留推进为 `TASK_ATTACHED`，把锚点推进为 `ATTACHED`，调用 `persistAttached()`。
8. 在 `fastPathMs` 内短轮询。
9. 快速终态进入 `completeSynchronously()`；其他情况进入 `suspend()`。

主要依赖字段包括 `pythonSandboxService`、`agentRunDatasetRegistry`、`pythonSandboxDispatchStore`、`dataAnalysisCapacityService`、`dataAnalysisCapacityProperties`、`dataAnalysisTerminalRecorder` 和 `fastPathMs`。

### 3.3 `run-42` 在这里发生什么

`executeDataIntense()` 读取 `runId=run-42`、`toolCallId=call-7`、`attempt=1`，生成稳定的操作标识 `operationId`。它根据 `todo-1` 产生的数据集元数据计算估算，并申请沙箱容量。

随后代码冻结创建规格：代码摘要、数据快照摘要、资源档位、内存限制、超时、运行环境版本和依赖摘要共同参与请求指纹。锚点先进入 `PREPARING`，其中已经包含操作标识 `operationId`、指纹、完整的 `createRequestJson`、容量预留、资源估算、数据快照、`todo-2` 位置和超时时间。

数据库确认 `PREPARING` 后才调用 `createTask()`。沙箱返回 `task-99` 后，容量预留变为 `TASK_ATTACHED`，锚点变为 `ATTACHED`。若 `task-99` 很快完成，`completeSynchronously()` 保存终态信封，释放容量并记录用量，随后向模型返回普通结果。

若短轮询窗口结束时任务仍在运行，`suspend()` 把容量预留推进到 `PENDING_TRANSFERRED`，把锚点推进到 `PENDING`，设置下一次轮询时间，再调用分发存储把锚点与运行状态一起持久化。只有该操作返回 `true`，方法才抛出 `ExternalToolJobPendingException(run-42, call-7, 1, ...)`。

### 3.4 失败或重启后的行为

数据元信息缺少行数或字节数时，代码返回 `DATA_ANALYSIS_ESTIMATE_UNAVAILABLE`，避免低估资源。任务超过硬限制或容量不足时分别返回过大或繁忙信息。

`persistPreparing()` 失败表示当前调用没有取得空锚点，代码会调用 `releasePreDispatch()` 释放尚未转交的容量预留，但当前调用没有检查这个释放动作的布尔返回值。`createTask()` 抛异常时，代码先调用 `getTaskByOperationId()`。查询到同一操作标识 `operationId` 与指纹时继续附着现有任务；明确未创建时才释放容量。结果仍不确定时保留 `PREPARING`，启动恢复可使用 `createRequestJson` 查询或重放相同请求。这个 `PREPARING` 修复属于启动恢复；在线后台协调器遇到空 `taskId` 会直接返回，因此进程不重启时记录可能继续停留在此状态。

沙箱响应指纹不同时，代码直接调用 `suspend()`：停止本次同步消费，并把任务转入已持久化的待处理状态。当前锚点仍保留 `autoResume=true` 与 `runDisposition=AUTO_RESUME`，源码没有写入“指纹不符”标记。因此后台以后仍可能按普通自动恢复流程继续处理；这里没有“等待人工审查”的保证。同步终态的任一步无法确认时也转入待处理状态，让可重复调用的完成器继续。

`suspend()` 中若容量状态转交冲突，或数据库无法同时保存 `PENDING` 与 `WAITING_TOOL_JOB`，方法会抛普通异常，不会抛出挂起控制信号。这样外层不会在缺少持久化责任交接时，把当前执行描述成已安全暂停。

### 3.5 与后续文件的连接

`PythonSandboxTools` 负责组装状态和决定转后台，数据库更新与 Redis 派生索引由 `PythonSandboxDispatchStoreImpl` 实现。后续文件说明 `persistPreparing()`、`persistAttached()` 和 `transferToPending()` 怎样把上述顺序落实到持久层。

## 4. `PythonSandboxDispatchStoreImpl.java`：让分发状态先进入 PostgreSQL

文件路径：

`agentLangchainService/src/main/java/world/willfrog/agentlangchain/tooljob/PythonSandboxDispatchStoreImpl.java`

### 4.1 为什么存在

`PythonSandboxTools` 位于 `agentToolsShared`，不能反向依赖 LangChain 服务模块中的数据库映射层、Redis 和恢复组件。因此公共模块声明 `PythonSandboxDispatchStore` 接口，LangChain 服务模块提供 `PythonSandboxDispatchStoreImpl`。

本实现还固定一条顺序：`PREPARING`、`ATTACHED`、`PENDING` 都先写入 PostgreSQL。只有 `PENDING` 已写入数据库，Redis 才保存待处理热副本与到期索引。

### 4.2 从哪里开始阅读

文件只有四个业务方法，适合按源码顺序阅读：

- `persistPreparing()`（23—27 行）：只接受 `anchorState=PREPARING`，并调用 `anchorService.claimPreparing(runId, anchor, EXECUTING)`；
- `persistAttached()`（30—36 行）：接受 `ATTACHED` 或同步终态 `TERMINAL`，按操作标识更新活跃锚点；
- `transferToPending()`（39—60 行）：要求 `anchorState=PENDING`，使用一次条件更新同时保存锚点，并将运行从 `EXECUTING` 修改为 `WAITING_TOOL_JOB`；
- `clearActive()`（63—65 行）：只有预期运行状态和操作标识都匹配时才清理。

主要字段是 `anchorService` 和 `redisCache`。本类不直接编写 SQL，条件更新由 `ToolJobAnchorService` 再交给数据库映射层。

### 4.3 `run-42` 在这里发生什么

创建 `task-99` 之前，`persistPreparing()` 要求 `run-42` 仍为 `EXECUTING` 且旧锚点为空。成功表示这次操作标识已取得分发资格。

沙箱返回 `task-99` 后，`persistAttached()` 使用同一操作标识，把任务标识与容量预留状态写回。若短轮询超时，`transferToPending()` 调用 `updateActiveAndStatus()`：同一条数据库更新保存 `PENDING` 锚点，并将 `run-42` 修改为 `WAITING_TOOL_JOB`。

数据库更新成功后，本类调用 `redisCache.atomicWritePendingAndDue()`。Redis分值对应下一次轮询时间，后台扫描可以按到期顺序取得 `run-42`。Redis 官方文档说明，有序集合用分值对成员排序，适合按时间取到期项；在 AlphaFrog 中它只承担发现工作，任务事实仍保存在 PostgreSQL。

### 4.4 失败或重启后的行为

任一状态或操作标识不匹配都会返回 `false`。调用方应检查这个布尔结果，不能把“方法未抛异常”当作取得写入资格。当前基线有三类未检查结果需要单独记住。第一，`PythonSandboxTools` 收到任务标识后首次调用 `persistAttached()`，没有读取返回值；后续同步终态的三次调用会检查。第二，`persistPreparing()` 失败分支调用 `releasePreDispatch()` 后没有检查释放结果。第三，`PythonSandboxDispatchStoreImpl.transferToPending()` 调用 `atomicWritePendingAndDue()` 后没有检查返回值。

`transferToPending()` 的数据库更新失败时不会写入 Redis，也不会允许上层抛出挂起信号。数据库成功后，`ToolJobRedisCache.atomicWritePendingAndDue()` 只有序列化失败才显式返回 `false`；执行 Redis Lua 脚本后没有检查返回的 `Long`，只要没有抛异常就返回 `true`。分发存储又忽略该布尔值；Redis 异常会被捕获并记录警告。无论返回值还是异常都不会回滚 PostgreSQL 中的待处理状态。`ToolJobReconciler.rebuildFromAnchors()` 和启动恢复会使用有限批次扫描从 PostgreSQL 重新建立 Redis 热副本与到期索引，因此这里只能说后续扫描可修复遗漏，不能证明写入当场已经成功。

同步 Python 完成后，`clearActive()` 只清理操作标识仍匹配的 `EXECUTING` 锚点。若 `run-42` 已经进入等待，或另一轮工具创建了新操作标识，旧调用不能删除新记录。

### 4.5 与下一层的连接

到这里，`run-42` 已经处于 `WAITING_TOOL_JOB`，`task-99` 与容量责任也已持久化。完整计划此前已由 `persistPlan()` 写入 `AgentRun.plan_json` 与 Redis；第三层的 `PREPARING` 锚点也已保存 `todoId/sequence`、数据集快照与摘要、资源估算和容量预留。旧工作线程仍有尚未补入检查点的已完成待办前缀、数据引用和实际工具调用次数，因此工作流现场还不完整。挂起控制信号会继续向上传播；第四层不会再次保存计划，而是冻结并补齐这三项，同时使用检查点版本对待办位置、快照和估算做窄合并与复核。

## 5. 把四个文件连成一次调用

```text
LangchainTodoNodeExecutor
  → 预先写入 todo-2 及其顺序
ToolRouterToolExecutor.executeWithContext / execute
  → 写入 run-42、用户/联网开关及 call-7 上下文
  → ToolRouter.invokeWithMeta
  → 预算、权重许可、参数规范化
  → PythonSandboxTools.executeDataIntense
  → PREPARING 写库
  → createTask 得到 task-99
  → ATTACHED 写库
  → 短轮询未完成
  → PENDING + WAITING_TOOL_JOB 同步写库
  → 抛出 ExternalToolJobPendingException
  → ToolRouter 与 ToolRouterToolExecutor 原样向上传播
```

阅读时可以用三个问题检查理解：

1. 为什么 `PREPARING` 必须早于 `createTask()`？因为 RPC 结果可能不确定，启动恢复需要稳定的操作标识和请求正文。
2. 为什么挂起信号不能变成工具失败字符串？因为沙箱仍在运行，模型尚未得到逻辑终态。
3. 为什么 Redis 写入失败不回滚数据库？因为 Redis 用于快速发现，PostgreSQL 保存任务事实和写入资格。
